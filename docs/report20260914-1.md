## 問題

`demo/mobile.html` 把剛解出來的字串當成預期值傳回去比(`expectedGtin: zx ? zx.text : state.expected`),
`demo/index.html` 則是 `state.expected = state.decoded` 三者恆等。結果是**掃到完全不同的箱子也顯示「比對符合」**,
而 CSV 欄位名 `expected_match` 緊鄰 `work_order`,語意無可爭辯。A-03 今天就印在對外展示的桌面測試台上。

## 改了什麼

兩支 demo 各加一個**「預期 GTIN」輸入欄**(`f-expected-gtin`),比對三態:

| 使用者填了什麼 | `expectedDataMatch` | 畫面 |
|---|---|---|
| 正確 GTIN | `true` | 比對符合 |
| 錯誤 GTIN | `false` | **比對不符** ← 修復前結構上不可能出現 |
| 沒填 / 只有空白 | `undefined` | 未比對 |
| 解碼失敗 | 不適用 | 整行留空(沒讀到就沒有比對可談) |

**三個實作決策值得記:**

1. **欄位放拍攝頁,不放清單頁的表頭三欄旁。** 快門按下那一刻就要拿它去比;放清單頁的話
   使用者會掃完 20 箱才填,而那 20 次比對早已用「未填」算完並存進 `scans` ——
   等於做出一個永遠顯示「未比對」的欄位。客戶 / 品名 / 工單號是「輸出報告前填寫」,補填不影響
   已完成的判定,性質不同。
2. **沒填時整個鍵都不傳,不傳空字串。** `engines/decode.ts` 判的是 `opts.expectedGtin !== undefined`,
   空字串會被當成「有預期值」而算出 `expectedDataMatch = false` —— **把「沒比」誤報成「不符」**。
3. **存進 `scans` 的是結論不是原料**,且 `expectedMatch` 用 `?? null` 而非 `|| null`:
   `null` = 未比對,與 `false` = 不符是兩件事,未來接 CSV 的 `expected_match` 欄時
   null 必須輸出空字串、不得輸出 false。
