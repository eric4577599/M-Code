## 1. 問題陳述(為什麼要改)

兩支 demo 的「預期值」都不是使用者給的,而是程式自己從解碼結果抄過來的:

| 檔案 | 現況 | 後果 |
|---|---|---|
| `demo/mobile.html:926` | `runDecode(..., { expectedGtin: zx ? zx.text : state.expected })`,而同一行上方 decoder 回傳 `data: zx.text` | 解碼成功時 `expectedDataMatch` **恆為 true**(拿自己比自己) |
| `demo/index.html:392, 402, 518` | `state.expected = state.decoded`、decoder 回傳 `data: state.decoded`、比對傳 `state.expected` | 三者恆等,**結構上不可能出現「不符」**;`:553`、`:582` 把「比對符合」印在畫面與可複製文字框 |

`src/export/csv.ts` 的 C9.4 固定欄序中,`expected_match` 緊鄰 `work_order` —— 欄位語意無可爭辯地是
「與工單上的預期 GTIN 相符」,而工單號從頭到尾沒被讀過。A-02(mobile)今天還沒輸出,
接上 CSV 匯出或 ERP 回寫就會輸出一整欄保證為 true 的「相符」;A-03(index)今天就在對外展示台的螢幕上。

**本輪的裁示是把功能做成真的,不是把它拿掉。**

## 2. 功能描述

兩支 demo 各新增一個「預期 GTIN」文字輸入欄,作為比對的**唯一**對照來源:

1. **有填** → 以使用者輸入(去頭尾空白後)當 `expectedGtin` 傳給 `runDecode`,畫面顯示「比對符合 / 比對不符」。
2. **沒填(空字串或全空白)** → **完全不傳 `expectedGtin` 這個鍵**,`expectedDataMatch` 維持 `undefined`,
   畫面顯示中性文字「未比對」。
3. 原本「拿解碼結果當預期值」的寫法全部移除。

**比對邏輯不自己寫**:`runDecode` 已處理(ITF-14 走 `gtinMatches` 的 GTIN-14 正規化比對,其餘符號別走字串相等)。
demo 的職責只有兩件:**把使用者填的值傳進去,或不傳**;以及**把三態如實顯示**。

### 2.1 tier 閘門:本欄位不加閘門(附理由)

`src/domain/flags.ts` 的 `FeatureFlag` 列舉沒有對應「預期值比對」的旗標,**不得自行發明**。
最接近的兩個都不適用:

- `decode_relative_light`(FREE 起即有)—— 解碼與其附帶的比對結果本來就在免費版。
- `csv_export` / `erp_api`(PAID 起)—— 閘的是**輸出通道**,不是輸入欄位;這兩處既有的 tier 判斷維持不動。

因此:**「預期 GTIN」欄位對所有 tier 一律可見可填**,HTML 內不得出現任何針對此欄位的 tier 判斷或文案
(依專案 `CLAUDE.md`:不得在 HTML 裡寫死 tier 判斷)。

### 2.2 欄位擺放位置(附論證)

| 檔案 | 位置 | 理由 |
|---|---|---|
| `demo/mobile.html` | 拍攝 view `#v-capture` 內,`.profSel`(`:311`)之下、`.hud`(`:313`)之上 | 預期 GTIN 是**拍攝前**就必須存在的對照基準:快門按下的那一刻就要拿它去比。若放在 `#v-list` 的表頭三欄旁,使用者會在掃完 20 箱之後才填,而那 20 次比對早已用「未填」算完並存進 `scans` —— 等於做出一個永遠顯示「未比對」的欄位。表頭三欄(客戶 / 品名 / 工單號)的性質是「**輸出報告前填寫**」,寫進 PDF 表頭即可,補填不影響已完成的判定;預期 GTIN 補填則會失效,兩者不同類,不可同處。 |
| `demo/index.html` | 拍攝頁 `#page-capture` 內,與「情境」卡片同一欄,置於 `#shutter`(`:235`)所在卡片之後、情境卡片之前(或情境卡片內上方);**必須與快門同頁可見** | 同上。桌面版按「檢驗」即立刻跑 `runDecode`,欄位必須在同一頁、按下之前可見可填。**不得**放進 `#page-list` 的「輸出資訊(列印 / 匯出前填寫)」表單。 |

實作端可在上述範圍內微調版位以配合既有 CSS class,但**必須滿足「與快門/檢驗鈕同頁且在其之前可見」**這條不變量。

## 3. 輸入 / 輸出定義

### 3.1 輸入欄位(兩檔必須完全一致)

| 項目 | 值 |
|---|---|
| 元素 | `<input type="text">` |
| `id` | `f-expected-gtin` |
| 標籤文字 | `預期 GTIN` |
| `placeholder` | `選填，例：14712345678907` |
| 初值 | 空字串(**不得**預填 `SAMPLE_DATA` 或任何解碼值) |
| 驗證 | **不做格式驗證、不擋輸入、不自動補零**。長度、校驗碼、GTIN-14 正規化一律交給 `src` 的 `gtinMatches` |

### 3.2 取值規則

兩檔各自提供一個取值輔助函式,語意必須相同:

```js
// 讀「預期 GTIN」欄:輸出去頭尾空白後的字串;沒填或只有空白時輸出空字串。
const expectedGtinInput = () => $("f-expected-gtin").value.trim();
```

### 3.3 傳給 `runDecode` 的方式(本輪最關鍵的一行)

```js
// 未填時**不可**傳 expectedGtin: "" —— decode.ts 判的是 `opts.expectedGtin !== undefined`,
// 空字串會被當成「有預期值」而算出 expectedDataMatch = false(把「沒比」誤報成「不符」)。
// 沒填就整個鍵都不要出現,讓 expectedDataMatch 維持 undefined,這是核心明文支援的誠實出口。
const exp = expectedGtinInput();
const decode = runDecode(decoder, session, exp ? { expectedGtin: exp } : {});
```

### 3.4 輸出:三態文字(兩檔字面值必須一致)

```js
// 比對標示:輸入 runDecode 回傳的 expectedDataMatch(true / false / undefined),
// 輸出畫面文字。undefined = 使用者沒填預期 GTIN → 誠實顯示「未比對」,
// 不可落回「符合」或「不符」——A-02 / A-03 的根因就是硬造出一個恆真的比對結果。
const MATCH_UNSET_TEXT = "未比對";
const matchLabel = (m) => (m === undefined ? MATCH_UNSET_TEXT : m ? "比對符合" : "比對不符");
```

| `expectedDataMatch` | 畫面文字 |
|---|---|
| `true` | `比對符合` |
| `false` | `比對不符` |
| `undefined`(未填預期值) | `未比對` |

`demo/index.html` 的 `:553`(`#decodeStatus`)與 `:582`(可複製文字框 `#resultText`)兩處三元式
`(decode.expectedDataMatch?"符合":"不符")` **必須改用 `matchLabel(decode.expectedDataMatch)`**,
不得保留任何把 `undefined` 折成「不符」的二元寫法。

`demo/mobile.html` 目前畫面上沒有比對字樣;本輪需在結果 view 的「辨識文字(解碼結果)」區塊
(`#decodedText`,`:365`)旁或其下顯示同一份 `matchLabel(...)` 結果,並一併寫進 `#resultText` 的可複製文字。

### 3.5 資料保存與(未來的)CSV

`demo/mobile.html` 的 `saveScan`(`:1897`)必須把這筆掃描當下的比對狀態存進 `scans`,否則算完即丟:

```js
expectedGtin: exp || "",                       // 那一刻使用者填的預期值(沒填 = 空字串)
expectedMatch: decode.expectedDataMatch ?? null, // true / false / null(null = 未比對)
```

**存結論不存重算所需的原料**,沿用該函式既有的 `why` 註解所立的原則。

CSV 對應(`src/export/csv.ts` 的 `expected_match` 欄,C9.4 固定欄序):

| 狀態 | `expected_match` 欄值 |
|---|---|
| 有填且相符 | `true` |
| 有填且不符 | `false` |
| **未填(未比對)** | **空字串**(留空,不得輸出 `false`) |

本輪 demo 尚未實作 CSV 匯出,故只規範 `scans` 的資料形狀與上表的對應規則;不得為此修改 `src/export/csv.ts`。

### 3.6 A-12:登出必須清掉本欄位

新欄位是使用者輸入的資料,共用機台上會殘留給下一個人,與客戶 / 品名 / 工單號同類。
**兩檔的 `doLogout` 都必須把 `f-expected-gtin` 加進既有的清除清單**:

```js
["f-customer", "f-product", "f-workorder", "f-expected-gtin"].forEach((id) => { $(id).value = ""; });
```

(`demo/index.html:868`、`demo/mobile.html:2190`。)漏掉這條 = 把 2026-09-11 剛修好的洩漏重新開一個洞。

## 6. Edge case 與預期行為

| # | 情境 | 預期行為 |
|---|---|---|
| E1 | 欄位空白 | 不傳 `expectedGtin` → `expectedDataMatch === undefined` → 顯示「未比對」,CSV 該欄留空 |
| E2 | 欄位只有空白字元 `"   "` | `trim()` 後為空 → 同 E1。**絕不可**傳 `expectedGtin: "   "`(那會算出 false) |
| E3 | 欄位前後帶空白 `" 14712345678907 "` | `trim()` 後傳入,比對照常成立 |
| E4 | 解碼失敗(不可讀) | `runDecode` 不回 `expectedDataMatch` → 顯示「✗ 不可讀」,**不附加任何比對文字**(不顯示「未比對」也不顯示「不符」) |
| E5 | ITF-14 且使用者填 13 碼 | 交給核心 `gtinMatches` 的 GTIN-14 正規化處理,demo 不補零、不驗校驗碼、不擋送出 |
| E6 | QR / DataMatrix / GS1-128 且大小寫或空白不同 | 核心走字串相等 → 判「比對不符」。這是正確行為,demo 不做正規化 |
| E7 | 填了值 → 清空 → 再按快門 | 每次檢驗都**重讀欄位當下值**,不快取到 `state`;清空後即回到「未比對」 |
| E8 | 切換符號別 / 情境 | 不得改寫 `f-expected-gtin` 的值(它屬使用者輸入,不屬情境資料);`syncSymbol` 只同步 `state.decoded` |
| E9 | 登出再登入 | 欄位為空(AC-7),新使用者不會繼承上一個人的預期值 |
| E10 | FREE tier 登入 | 欄位照樣可見可填、比對照樣顯示;閘門只在既有的 CSV / ERP / 報告輸出處,本欄位不加閘門 |
| E11 | 情境模擬(無相機)路徑 | 與真實解碼走同一條取值與傳參規則,不得另立一套「模擬時直接給 true」的分支 |
