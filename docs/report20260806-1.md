## 1. 診斷:延遲確實存在,而且它造成的是**判定失效**不是畫面失效

我沒有從描述推測,直接把取幀路徑的時序從程式碼讀出來:

| 時間點 | 發生什麼 | 位置 |
|---|---|---|
| −500…0 ms | `measureFrame` 量**預覽**幀 → 四項讀數 → 燈號綠、快門 ARMED | `mobile.html` 每 500ms |
| 0 | 按下快門 → `inspecting = true` → **即時量測整段停止** | `measureFrame` 開頭 |
| 0…800 ms | L1 `takePhoto()`(手機快門延遲,且會重跑 AF/AE) | `captureViaImageCapture` |
| 0…500 ms | L2 `applyConstraints` 升壓 → 一到目標寬就放行 | `captureViaConstraints` |
| T | **這一張**才是被解碼、被分級的影像 | — |

**缺陷 ① —— 判定的幀不是被分析的幀。**
燈號依據的是快門前 ≤500ms 的預覽,被分級的是快門後 ≤800ms 的照片,最壞相隔約 **1.3 秒**。
更嚴重的是昨天才加的「本張閘門」(裁示 D5③):它的註解寫著「讓報告第一次講得出這張照片的
實際拍攝品質」,但光度四項讀的是 `state.gate` 的預覽殘值 —— **從未量過被分析的那張影像**。
報告印「本張閘門 全部 OK」時,那四欄講的是另一張影像。這是誠實性缺陷,不只是精度問題。

**缺陷 ② —— L2 抓的是模式切換後的第一幀。**
`applyConstraints` 換解析度等於換相機模式,AE/AF 會重新收斂,而 `waitForVideoWidth`
一到目標寬就 resolve —— 放行的正是收斂中的那一幀。

**而且從來沒有任何一處量過實際延遲**,所以「似乎會有延遲」到今天還是猜的。

## 2. 修法

**核心不是把延遲消掉**(消不掉:`takePhoto` 的延遲在瀏覽器與韌體裡),
而是**把判定改成量在被分析的那張影像上** —— 延遲多久都不影響結論的正確性。

| # | 改動 | 位置 |
|---|---|---|
| F1 | 抽出 `measureQuality(src, w, h)`,預覽與快門照走**同一條 320px 取樣路徑**;`shotGate` 改吃照片自己的讀數 | `mobile.html` |
| F2 | 實測並記錄快門延遲毫秒數 + 對焦相對預覽比值 → `lastShotInfo` → 清單 → PDF | `mobile.html` |
| F3 | `assessShotFreshness` 純函式:「預覽過了、照片沒過」→ 具名告警並建議重拍 | `imgproc.js` |
| F4 | L2 升壓協商完成後多等 `SETTLE_FRAMES` 讓 AE/AF 沉澱 | `mobile.html` |
| F5 | 快門忙碌標籤「檢驗中…」→「**拍攝中 — 請維持不動**」 | `mobile.html` |
| F6 | L2 的降壓等待**移出關鍵路徑**(同日追加,見 §6) | `mobile.html` |

F5 看似瑣碎,但它是唯一一處告訴使用者「按完之後還在拍」的訊息。原本的「檢驗中…」
會讓人以為已經拍完,按完就把手機移開 —— 正好落在延遲窗口裡。

### 為什麼取樣寬固定 320

`varianceOfLaplacian` 是高頻能量的變異數,隨取樣密度系統性變動,而對焦門檻
(`policies.ts`,依規格 §6.1 凍結)校在這個尺度上。預覽與快門照走同一尺度,
同一組門檻才適用、兩邊的數字才可互比。這也是把它抽成共用函式的理由 ——
兩處各寫一份就會在日後靜默漂開。

### 實作中被推翻的一個判斷

**第一版打算用「照片 varLap ÷ 預覽 varLap < 0.6」當 stale 的判準,後來拿掉了。**
兩者雖同為 320px,來源尺度不同(預覽由 1280 縮下來、照片可能由 4032 縮下來),
後者抗鋸齒平均更重,比值天生帶系統性偏差。**本輪探針在同一張靜止合成圖上實測到
這個比值在 1%–137% 之間擺動** —— 未經實拍校準就拿它當門檻只會製造偽陽性。
最後改成:比值照算照記錄,但**只作診斷數字**;判定完全走既有的已校準絕對門檻,
**本輪沒有引入任何新的判定門檻**。

舊程式碼會照抄那個 OK,把一張糊掉的照片記成「對焦正常」。

**測試 C — 眩光路徑(驗「有出等級 + 告警」並存)。** 糊到對焦不過時 ZXing 已先解不出來,
走的是不可量測路徑;改在快門後才加眩光:

```

本張閘門 眩光 FAIL、楞痕透印 FAIL、白平衡 WARN、解析度 WARN
⚠ 拍攝當下角度已變動 — 這張照片的眩光超標,量測值不可採信
```

這正是最危險的組合:**一個「通過」的等級長在一張不可信的照片上**,現在會被具名標出來。
接著同樣條件不加眩光再拍一次,告警正確消失、等級仍為 B —— 確認不會跨筆殘留。

### 3.3 沒驗到的(誠實列出)

- **`快門延遲 1992ms` 不是有效的實機數字。** 自動化跑在非前景分頁,`requestAnimationFrame`
  與 `requestVideoFrameCallback` 都不觸發,三段等待(500 + 200 + 300ms)**每次都吃滿逾時**。
  真實裝置上會短得多。這個數字只證明欄位有接上,不證明延遲有多長。
- **`SETTLE_FRAMES` 與 `SLOW_SHUTTER_MS = 400` 是推理值不是量測值。** 前者在非前景分頁
  完全沒發揮作用(rVFC 不觸發),等於**這一輪它一次都沒真的沉澱過**。
- **F4 會增加延遲,方向與 Eric 的抱怨相反。** ⚠ **這一條當天就被 Eric 推翻並改掉了,
  3 幀 → 1 幀,見 §6** —— 下面這段保留的是改之前的判斷與理由,不是現況。
  原文:之所以仍採用,是因為它換到的是「被分析的幀是可用的」;而就算等不夠,
  F1 也會把糊掉的那張抓出來告警。**這是本輪唯一一個「reasoned 而非 measured」的改動。**
- **一次實拍都沒有。** 全部是合成圖與假相機。
- **對焦門檻在這張合成圖上比 ZXing 還寬容** —— 糊到對焦不過(blur 5)時,解碼在 blur 3
  就已經失敗。所以「解碼成功 + 對焦 FAIL」這個組合在本輪的合成圖上**做不出來**,
  改用眩光路徑替代。這是測試影像的性質(6px 模組、近二值對比),不是分支失效的證據。

## 4. 探針原始碼(沿用上一輪的紀律:產生器留在報告裡)

`video.videoWidth` 永遠是 0,相機看起來像「開不起來」。

## 6. 同日追加:F4 下修 + F6(Eric 現場判斷推翻了 F4 的折衷)

上線後 Eric 反映「**L2 的 3 幀、快門與間隔都過慢,反而會因手震導致問題**」。
這推翻了 F4 原本的折衷,**而且推翻得對**。我原本把「AE/AF 未收斂」與「手震位移」
當成對等的兩個風險去折衷,實際上兩者不對等:

> **等待本身就是手震窗口。** 手持拍攝下,多等的每一幀都在累積位移,而位移造成的動態
> 模糊是**連續且必然**的;AE/AF 未收斂只是**一次性的過渡**。拿「一定會發生的」去換
> 「可能發生的」是賠本的,方向錯了。

### 改了什麼

| 段 | 原本 | 現在 | 影響拍到哪一幀? |
|---|---|---|---|
| `waitForVideoWidth` 升壓側 | ≤500ms | 不變 | **是** —— 要等到新解析度,拿掉就白升壓了 |
| `waitVideoFrames` 沉澱 | 3 幀 / ≤200ms | **1 幀 / ≤60ms** | 是,只保留「不抓切換當下那一幀」 |
| `finally` 降壓 + 等待 | ≤300ms,**`await` 在關鍵路徑上** | **移出關鍵路徑** | **否** |

**F6 是零代價的純收益,而且是我第一輪該看出來卻沒看出來的。** 那段降壓等待發生在
**照片已經取到之後**,唯一作用是讓 `inspecting` 涵蓋整段串流過渡(擋 `measureFrame`
量到過渡幀),與「拍到哪一幀」完全無關。原本寫成 `await`,於是連帶把 `inspectReal`
與結果頁整條路往後推 300ms —— 純粹是使用者多等,沒有換到任何品質。

改法:把 promise 存進 `pendingDownscale` 不在該處 await,交給 `inspect()` 的 `finally`
在**清除 `inspecting` 之前**等它。**保護區間一模一樣**,但影像分析(ZXing + ROI + 計量)
與降壓變成並行跑。它有 `if (wBefore > PREVIEW_W)` 守衛,**只有真的升壓超過 1280 才發生**
—— 省到的 300ms 正好落在實機(升到 4032),不是落在低解析度串流上。

### 驗證,以及一個必須講清楚的限制

**⚠ 本機探針量不出這兩項的時間效益,一毫秒都量不出。**
自動化跑在非前景分頁,瀏覽器把 `setTimeout` 對齊到約 1 秒 ——
實測 `setTimeout(500)` → **998ms**、`setTimeout(60)` → **471ms**。
所有逾時被拉平,改動前後量到的 `快門延遲` 都是 **1993 / 1989 / 1988ms**,一模一樣。
**先前報告裡那個 1992ms,和現在這個 1993ms,兩者都不是延遲的真實量測值。**

所以本輪只做了功能驗證(連拍三張):

| 情境 | 告警 | 等級 | 拍完後快門標籤 |
|---|---|---|---|
| 正常 | 無 | B | 正常(未卡在「拍攝中」) |
| 快門後起眩光 | **有** | B | 正常 |
| 再拍一張正常 | 無(正確清除) | B | 正常 |

第三欄是 F6 的關鍵驗證:`inspecting` 每次都正確釋放,代表 `pendingDownscale` 的
await 有被執行到、沒有把快門鎖死,也沒有 unhandled rejection(console 全乾淨)。

**時間效益必須在實機上量。** PDF 的 `取幀時序` 欄就是為此存在的。

## 7. 同日追加:離線外殼(PWA)—— 解掉「網頁打不開」

Eric 回報手機開 `m-code.ericchh.work` 一直轉圈載不完。**不是程式壞掉,是往返次數。**

### 診斷(全部實測)

| 量到什麼 | 數字 | 意思 |
|---|---|---|
| 一次載入的請求數 / 總量 | 20 個 / 176 KB | 量很小,不是頻寬問題 |
| 單一 1 KB 模組,經隧道 | 660 ms | 幾乎全是網路往返 |
| 同一支,origin 本機 | ≈ 1 ms | 伺服器本身完全不是瓶頸 |
| Cloudflare 邊緣 | `cf-ray` = **SIN** | 台灣 → 新加坡 → 台灣 |
| 模組匯入瀑布 | **4 層** | 要先下載完 `dist/index.js` 才發現還有 15 支子模組 |
| 快取策略 | `no-store` | **每次開頁都完整重抓 20 個檔** |

兩段修正:

**① `modulepreload`** —— 在 `<head>` 預先宣告 15 支子模組,瀑布 4 層 → 1 層(18 檔同時起跑)。
DOMContentLoaded **3 760 → 3 410 ms**。改善有限,因為瓶頸只是換人:20 個請求還是要跨海。

**② 離線外殼(Service Worker)** —— 這才是真正的解法。

### 實測結果

| | 修正前 | 加 modulepreload | 加離線外殼 |
|---|---|---|---|
| DOMContentLoaded | 3 760 ms | 3 410 ms | **67–70 ms** |
| 網路傳輸 | 176 KB | 176 KB | **0 KB** |
| 由外殼供應 | — | — | **20 / 20** |

**54 倍。** 而且第二次起完全不碰網路 —— 這同時就是「瓦楞廠現場沒網路」的解法,
檢驗流程本來就不需要連線(所有量測與分級都在裝置上)。

### 更新策略:刻意不自動生效

這個專案踩過「線上沒更新」的坑(2026-07-21 曾有 26 個 commit 沒上線),
多一層快取就多一種同樣的失敗模式。所以:

- **`install` 內不 `skipWaiting`** —— 新版只進 waiting,舊版繼續**完整**服務,
  不會出現「新 HTML 配舊 JS」的混搭窗口。
- **由頁面跳橫幅,使用者按了才切換** → `postMessage` → `skipWaiting` → 重載。
- **快取名帶內容雜湊**,`deploy/stamp-sw.py` 在 rsync 之後蓋章。任何外殼檔案有變 → 章不同 →
  快取名不同 → 瀏覽器偵測到新的 `sw.js`。**不靠人記得改版本號。**
- `m-code-serve.py` 的 `no-store` **一行未動** —— 外殼接手之後它不再是瓶頸,
  而留著它可以讓 `sw.js` 本身永遠是最新的。原本要問的「要不要放寬快取」這題自動消失了。

更新路徑實跑驗證(改一支外殼檔案 → 重新蓋章 → `reg.update()`):

```
橫幅出現          ✓「有新版本可用 — 更新後再繼續檢驗」
新版狀態          waiting(未自動切換)✓
舊快取            仍在服務,頁面照常可用 ✓
按下「立即更新」  → 自動重載 → 舊快取已清 ✓ → 單一快取 ✓
```

### 實跑抓到、靜態檢查抓不到的一個漏網

第一版外殼漏了 `icons/*.png`。manifest 一被解析,瀏覽器就會去抓圖示 ——
離線時那支請求會打不到網路。**靜態檢查看不出「誰會被請求」**,是實跑逐一比對
「啟動所需資源 vs 快取命中」才發現的。已補進外殼,並在測試加了對應守門。

### 守門測試

`tests/pwa-shell-sync.test.ts`(12 條)。加了外殼之後,「這個 app 由哪些檔案組成」變成
**三份**清單:`src/index.ts`(真來源)、HTML 的 `modulepreload`、`sw.js` 的 `SHELL`。
三者一漂開就是**沒有症狀的故障** —— 少一支 → `addAll` 整批失敗 → 使用者完全沒有離線能力,
而線上一切正常,沒有任何人會發現。測試把三者釘在一起,另外釘住更新策略
(`install` 內不得有 `skipWaiting(` 呼叫)與版本章的存在。

測試 481 → **493**(16 檔)。`src/` 零變更,門檻一行未動。

### 沒驗到的

- **沒有在真正斷網的情況下測過。** 驗的是等價條件:啟動所需的 20 個資源全部在 Cache 命中、
  網路傳輸 0 KB —— 斷網時 SW 會用同一份回應答覆。但「把網路關掉再開 app」沒有實際做過。
- **沒有在手機上測過。** iOS 的 PWA 行為(加到主畫面、standalone、SW 生命週期)與桌面
  Chrome 有差異,特別是 iOS 會較積極回收 SW。
- **圖示是程式產生的**(純 Python PNG 編碼器,不加相依套件),不是設計稿。
- **`m-code-serve.py` 沒有動**,所以第一次安裝仍然要跨海抓 26 個檔案 —— 第一次開還是慢,
  只有第二次起才是 70ms。
