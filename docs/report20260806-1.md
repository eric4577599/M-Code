## 1. 診斷:延遲確實存在,而且它造成的是**判定失效**不是畫面失效

我沒有從描述推測,直接把取幀路徑的時序從程式碼讀出來:

| 時間點 | 發生什麼 | 位置 |
|---|---|---|
| −500…0 ms | `measureFrame` 量**預覽**幀 → 四項讀數 → 燈號綠、快門 ARMED | `mobile.html` 每 500ms |
| 0 | 按下快門 → `inspecting = true` → **即時量測整段停止** | `measureFrame` 開頭 |
| 0…800 ms | L1 `takePhoto()`(手機快門延遲,且會重跑 AF/AE) | `captureViaImageCapture` |
| 0…500 ms | L2 `applyConstraints` 升壓 → 一到目標寬就放行 | `captureViaConstraints` |
| T | **這一張**才是被解碼、被分級的影像 | — |

**缺陷 ① —— 判定的幀不是被分析的幀。**
燈號依據的是快門前 ≤500ms 的預覽,被分級的是快門後 ≤800ms 的照片,最壞相隔約 **1.3 秒**。
更嚴重的是昨天才加的「本張閘門」(裁示 D5③):它的註解寫著「讓報告第一次講得出這張照片的
實際拍攝品質」,但光度四項讀的是 `state.gate` 的預覽殘值 —— **從未量過被分析的那張影像**。
報告印「本張閘門 全部 OK」時,那四欄講的是另一張影像。這是誠實性缺陷,不只是精度問題。

**缺陷 ② —— L2 抓的是模式切換後的第一幀。**
`applyConstraints` 換解析度等於換相機模式,AE/AF 會重新收斂,而 `waitForVideoWidth`
一到目標寬就 resolve —— 放行的正是收斂中的那一幀。

**而且從來沒有任何一處量過實際延遲**,所以「似乎會有延遲」到今天還是猜的。

## 2. 修法

**核心不是把延遲消掉**(消不掉:`takePhoto` 的延遲在瀏覽器與韌體裡),
而是**把判定改成量在被分析的那張影像上** —— 延遲多久都不影響結論的正確性。

| # | 改動 | 位置 |
|---|---|---|
| F1 | 抽出 `measureQuality(src, w, h)`,預覽與快門照走**同一條 320px 取樣路徑**;`shotGate` 改吃照片自己的讀數 | `mobile.html` |
| F2 | 實測並記錄快門延遲毫秒數 + 對焦相對預覽比值 → `lastShotInfo` → 清單 → PDF | `mobile.html` |
| F3 | `assessShotFreshness` 純函式:「預覽過了、照片沒過」→ 具名告警並建議重拍 | `imgproc.js` |
| F4 | L2 升壓協商完成後多等 `SETTLE_FRAMES`(3 幀 / 上限 200ms)讓 AE/AF 沉澱 | `mobile.html` |
| F5 | 快門忙碌標籤「檢驗中…」→「**拍攝中 — 請維持不動**」 | `mobile.html` |

F5 看似瑣碎,但它是唯一一處告訴使用者「按完之後還在拍」的訊息。原本的「檢驗中…」
會讓人以為已經拍完,按完就把手機移開 —— 正好落在延遲窗口裡。

### 為什麼取樣寬固定 320

`varianceOfLaplacian` 是高頻能量的變異數,隨取樣密度系統性變動,而對焦門檻
(`policies.ts`,依規格 §6.1 凍結)校在這個尺度上。預覽與快門照走同一尺度,
同一組門檻才適用、兩邊的數字才可互比。這也是把它抽成共用函式的理由 ——
兩處各寫一份就會在日後靜默漂開。

### 實作中被推翻的一個判斷

**第一版打算用「照片 varLap ÷ 預覽 varLap < 0.6」當 stale 的判準,後來拿掉了。**
兩者雖同為 320px,來源尺度不同(預覽由 1280 縮下來、照片可能由 4032 縮下來),
後者抗鋸齒平均更重,比值天生帶系統性偏差。**本輪探針在同一張靜止合成圖上實測到
這個比值在 1%–137% 之間擺動** —— 未經實拍校準就拿它當門檻只會製造偽陽性。
最後改成:比值照算照記錄,但**只作診斷數字**;判定完全走既有的已校準絕對門檻,
**本輪沒有引入任何新的判定門檻**。

## 3. 驗證

### 3.1 自動化

`npm run typecheck` 通過;`npm test` **14 檔 471 測試**全綠(457 → 471,+14);`npm run build` 通過。

新增測試鎖住的是**判定的方向性**:只有「預覽過了、照片沒過」才算 stale。
反向(預覽本來就沒過)明文斷言**不算** —— 那是使用者沒對準,與延遲無關,混為一談
會讓使用者照著錯的提示去做無效的重拍。另有比值不參與判定、快門偏慢不等於拍壞、
除以零、退化輸入、以及「每個原因碼的文案都必須講『這張照片』而非符號品質」(定位護欄)。

### 3.2 8765 測試台實跑(假相機探針)

探針走 loopback-only 的 127.0.0.1:8799 服務 repo 本體 —— **8765 服務的是 `~/m-code-site`,
它經 cloudflared 對外**,上一輪把探針放進去是錯的,本輪確認對外 404、驗後即刪。

**測試 A — 正常拍(全程不動):**

```
本張閘門 楞痕透印 FAIL、白平衡 WARN、解析度 WARN
取幀時序 快門延遲 1992ms(偏慢) · 對焦相對預覽 134%
→ 等級 B · 通過 · 無告警
```

**測試 B — 模擬「延遲窗口內畫面變糊」**(同步區塊內設糊再按快門,預覽讀數必然還是清晰那筆):

```
本張閘門 對焦 FAIL、楞痕透印 FAIL、白平衡 WARN
取幀時序 快門延遲 1978ms(偏慢) · 對焦相對預覽 1%
⚠ 拍攝當下畫面已變動 — 這張照片的對焦不足,量測值不可採信
```

**`本張閘門 對焦 FAIL` 就是這次修正的證據** —— 預覽當下是清晰的(面板對焦 OK),
舊程式碼會照抄那個 OK,把一張糊掉的照片記成「對焦正常」。

**測試 C — 眩光路徑(驗「有出等級 + 告警」並存)。** 糊到對焦不過時 ZXing 已先解不出來,
走的是不可量測路徑;改在快門後才加眩光:

```
等級 B · 通過(門檻 ≥ C)
本張閘門 眩光 FAIL、楞痕透印 FAIL、白平衡 WARN、解析度 WARN
⚠ 拍攝當下角度已變動 — 這張照片的眩光超標,量測值不可採信
```

這正是最危險的組合:**一個「通過」的等級長在一張不可信的照片上**,現在會被具名標出來。
接著同樣條件不加眩光再拍一次,告警正確消失、等級仍為 B —— 確認不會跨筆殘留。

### 3.3 沒驗到的(誠實列出)

- **`快門延遲 1992ms` 不是有效的實機數字。** 自動化跑在非前景分頁,`requestAnimationFrame`
  與 `requestVideoFrameCallback` 都不觸發,三段等待(500 + 200 + 300ms)**每次都吃滿逾時**。
  真實裝置上會短得多。這個數字只證明欄位有接上,不證明延遲有多長。
- **`SETTLE_FRAMES = 3` 與 `SLOW_SHUTTER_MS = 400` 是推理值不是量測值。** 前者在非前景分頁
  完全沒發揮作用(rVFC 不觸發),等於**這一輪它一次都沒真的沉澱過**。
- **F4 會增加約 100ms 延遲**(30fps 下 3 幀),方向與 Eric 的抱怨相反。之所以仍採用,
  是因為它換到的是「被分析的幀是可用的」;而就算等不夠,F1 也會把糊掉的那張抓出來告警。
  **這是本輪唯一一個「reasoned 而非 measured」的改動**,實機資料回來後應優先重估。
- **一次實拍都沒有。** 全部是合成圖與假相機。
- **對焦門檻在這張合成圖上比 ZXing 還寬容** —— 糊到對焦不過(blur 5)時,解碼在 blur 3
  就已經失敗。所以「解碼成功 + 對焦 FAIL」這個組合在本輪的合成圖上**做不出來**,
  改用眩光路徑替代。這是測試影像的性質(6px 模組、近二值對比),不是分支失效的證據。

## 4. 探針原始碼(沿用上一輪的紀律:產生器留在報告裡)

做法同 `report20260805-1.md` §5:讀 `demo/mobile.html`、插 patch、另存 `demo/_probe.html`,
驗後即刪。本輪比上一輪多兩處,以及**兩個踩到的坑**:

**坑 ①:插入點要用 `lastIndexOf("</body>")`。**
`exportPdf` 組 PDF 用的 HTML 字串裡也有一個 `</body>`,`String.replace` 吃字串樣式只換
第一個 —— 探針會被塞進模組的樣板字串內,整個模組語法錯誤。

**坑 ②:畫布重繪要用 `setInterval` 不能用 `requestAnimationFrame`。**
自動化跑在非前景分頁,rAF 完全不觸發 → 畫布不更新 → `captureStream` 一幀都不產生 →
`video.videoWidth` 永遠是 0,相機看起來像「開不起來」。

```js
// ① ARMED 檢查放行(合成圖必然眩光/楞痕不過)
s = s.replace(`const gate = evalGate(); if (gate.state !== "ARMED") return;`,
              `const gate = evalGate(); /* PROBE */`);
// ②③ 假相機 + focalLength,插在最後一個 </body> 之前
const at = s.lastIndexOf("</body>");
s = s.slice(0, at) + probe + s.slice(at);
```

探針內容(ITF 編碼表沿用 `report20260805-1.md` §5,此處只記本輪新增的兩個旋鈕):

```js
const PROBE = { blur: 0, glare: 0 };
function paint() {
  const g = fake.getContext("2d");
  g.filter = "none";
  g.fillStyle = "#d8c9a8"; g.fillRect(0, 0, CW, CH);           // 牛皮箱面
  g.filter = PROBE.blur ? `blur(${PROBE.blur}px)` : "none";    // 失焦模擬
  /* …bearer bar 與條空… */
  if (PROBE.glare) { g.filter = "none"; g.fillStyle = "#ffffff";
    g.fillRect(0, 0, CW, Math.round(PAD_Y * PROBE.glare)); }   // 眩光模擬(只蓋靜區,不殺解碼)

const stream = fake.captureStream(30);
```

## 5. 給下一輪的提醒

1. **`assessShotFreshness` 與 `assessMeasurability` 是同一條紀律的兩支閘口** ——
   「這種情況該不該相信這個結果」的判斷一律往 `imgproc.js` 加,不寫進 `mobile.html`。
2. **實機第一件事是把延遲量出來。** `取幀時序` 已進 PDF,雙平台各拍幾張就有數字。
   拿到之後才有資格重定 `SETTLE_FRAMES` 與 `SLOW_SHUTTER_MS`。
3. **同時記下 `對焦相對預覽 xx%` 的分布。** 那是把比值升格成判準所需要的唯一資料;
   在它穩定之前不要拿它當門檻。
4. **`captureViaConstraints` 的 `finally` 裡有 300ms 降壓等待,發生在照片已經取到之後** ——
   它不影響拍到哪一幀,只延後使用者看到結果。本輪沒動它(那是刻意的設計,見該處註解),
   但現在它已經被算進 `快門延遲` 裡了,實機數字回來時要記得扣掉這一段再解讀。
