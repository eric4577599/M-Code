## 1. A-07 — `getWorkOrder` 加型別守衛(`src/erp/client.ts`)

### 1.1 問題

`getWorkOrder` 目前 `return res.body as WorkOrder`,裸 cast。`WorkOrder.acceptance.requiredGrade` 是 pass/fail 的判準,一旦值不是 `A|B|C|D|F`(例如小寫 `'c'`、`'B+'`、`null`),下游 `evaluateAcceptance` 會:

- `isAtLeast()` 查 `LETTER_NOMINAL_SCORE[required]` 得 `undefined` → 比較恆 false → `pass=false`
- `letterToBandCut()` 找不到字母 → 回 0 → `marginScore = overallScore − 0 = overallScore`

於是出現 `pass=false` 配 `margin=+3.60`,打破 `acceptance.ts` JSDoc 承諾的 **`margin ≥ 0 ⟺ pass`** 不變量。`marginScore` 是餵給預警與趨勢監控的數字,這會讓下游數字說謊。

### 1.2 功能描述

在 `src/erp/client.ts` 內新增一支型別守衛 `isWorkOrder(value: unknown): value is WorkOrder`,比照既有 `isOAuthTokenResponse`(同檔案)的寫法與位置慣例。`getWorkOrder` 在 HTTP 狀態檢查通過後、回傳前先驗 body;不合格則擲 `ErpHttpError`。

### 1.3 輸入 / 輸出定義

`isWorkOrder` 對以下全部成立時才回 `true`:

| 欄位 | 規則 |
|---|---|
| `value` | 是非 null 的 object(不是陣列、不是字串) |
| `id` | `typeof === "string"` |
| `customer` | `typeof === "string"` |
| `symbology` | ∈ `ITF14 \| GS1_128 \| CODE128 \| QR \| DATAMATRIX` |
| `expectedGtin` | 缺席(`undefined`)或 `typeof === "string"` |
| `acceptance` | 是非 null 的 object |
| `acceptance.requiredGrade` | ∈ `A \| B \| C \| D \| F`(**大小寫敏感**,`'c'` 不合格) |
| `acceptance.xDimSpecMm` | `Number.isFinite()` 為 true |
| `acceptance.quietZoneMinX` | `Number.isFinite()` 為 true |

`getWorkOrder` 行為:

- body 通過守衛 → 回傳該 `WorkOrder`(與現行行為完全相同)。
- body 未通過守衛 → 擲 `ErpHttpError(res.status, res.body)`,亦即帶回實際 HTTP 狀態與原始 body 供除錯。**不得**回傳半個物件、不得就地修補欄位、不得替 `requiredGrade` 補預設值。
- 非 2xx 的既有路徑(含 401 清 token 快取)不變,順序仍是「先檢查狀態碼、再檢查格式」。

### 1.4 允許值集合的來源

`GradeLetter` 的合法值以 `src/domain/scale.ts` 的 `LETTER_NOMINAL_SCORE` / `GRADE_BAND_CUTS` 為單一事實來源,不要在 `client.ts` 手抄一份字面陣列後任其漂移;`Symbology` 可用本地 `readonly` 集合(型別層已有 union,新增集合需與之對齊)。無論採哪種寫法,**都不得改動任何分數值**。

### 1.5 驗收標準(每條可被測試驗證)

- AC-07-1:`getWorkOrder` 收到合法 body → 回傳值與 body 深度相等,既有 `tests/erp.test.ts` 相關案例全綠。
- AC-07-2:`requiredGrade` 分別為 `'c'`、`'B+'`、`null`、`undefined`、數字 `2` 時,`getWorkOrder` **擲出** `ErpHttpError`,而非回傳物件。
- AC-07-3:**重演稽核情境**——一支測試以 `evaluateAcceptance` 搭配 overallScore 3.60 的 `GradeResult`,證明「凡是能通過 `isWorkOrder` 的 `requiredGrade`,`marginScore >= 0` ⟺ `pass === true`」;並斷言 `'c'`/`'B+'`/`null` 這三種 body 在新行為下根本到不了 `evaluateAcceptance`(`getWorkOrder` 先擲錯),因此不可能再出現 `pass=false` 配 `margin=+3.60`。
- AC-07-4:缺 `acceptance`、`acceptance` 為 `null`、`acceptance.xDimSpecMm` 為 `NaN` / 字串、`id` 非字串、`symbology` 為 `"ITF-14"`(錯拼)時,皆擲 `ErpHttpError`。
- AC-07-5:`expectedGtin` 缺席時仍通過守衛(選填欄位不得被誤判為不合格)。
- AC-07-6:body 為 `null`、字串、陣列時皆擲 `ErpHttpError`,不擲 `TypeError`。

## 2. A-09 — token 端點「200 + 格式錯」必須收斂成 FAILED(`src/erp/client.ts`)

### 2.1 問題

`getToken` 在 HTTP 200 但 body 非 OAuth 格式時擲 `ErpHttpError(200, ...)`。`syncOne` 的 catch 只把 `status ∈ [400,500)` 收成 FAILED,200 落到 transient 分支 → 整個佇列永遠 `QUEUED`,反覆重送。成因是設定錯誤(例如反向代理攔截回一頁 HTML),重試一萬次也不會好,與 `syncOne` 註解宣稱的「避免整個佇列無限期滯留重送」直接矛盾。

### 2.2 功能描述

讓「回應格式錯」成為**可區分的永久性錯誤**。實作擇一:

- (建議)新增 `export class ErpMalformedResponseError extends ErpHttpError`,`name = "ErpMalformedResponseError"`,建構子沿用 `(status, body)`;或
- 在 `ErpHttpError` 上加一個可判別的唯讀欄位(如 `readonly malformed: boolean`)。

採用繼承寫法時,**既有 `err instanceof ErpHttpError` 的判斷仍會成立**,所以 `syncOne` 的分支順序必須是:先判 malformed → FAILED,再判 4xx → FAILED,其餘 → QUEUED。

`getToken` 在 `!isOAuthTokenResponse(res.body)` 且狀態碼本身是 2xx 時,擲這個新的可區分錯誤;狀態碼非 2xx 時仍擲原本的 `ErpHttpError(status, body)`(這樣 5xx 才不會被誤歸)。

### 2.3 輸入 / 輸出定義(`syncOne` 的完整 outcome 表,改動後)

| 觸發情境 | outcome | reason |
|---|---|---|
| POST 2xx | `SYNCED` | —(附 `inspectionId`,若 body 有) |
| POST 401 | `QUEUED` | `HTTP 401`(快取已清,下次帶新 token 重試) |
| POST 其餘 4xx | `FAILED` | `HTTP <status>` |
| POST 5xx / 其他非 2xx | `QUEUED` | `HTTP <status>` |
| `getToken` 擲 4xx | `FAILED` | 錯誤訊息 |
| **`getToken` 擲 200 + 非 OAuth body** | **`FAILED`** | 錯誤訊息(含可辨識字樣) | 
| `getToken` 擲 5xx | `QUEUED` | 錯誤訊息 |
| 網路錯誤 / timeout(非 `ErpHttpError`) | `QUEUED` | `err.message` |

粗體那列是本條唯一的行為變更;其餘七列必須與改動前**逐格相同**。

### 2.4 驗收標準

- AC-09-1:**重演稽核情境**——Transport 對 `/oauth/token` 回 `{ status: 200, body: "<html>…</html>" }`,`processQueue([insp-1, insp-2])` 的兩筆 outcome 皆為 `FAILED`(舊行為是兩筆 `QUEUED`)。
- AC-09-2:token 端點回 200 但 body 為 `{}`、`null`、`{ access_token: 123 }`、`{ access_token: "x" }`(缺 `expires_in`)時,同樣收斂為 `FAILED`。
- AC-09-3:token 端點回 500(body 任意)→ 兩筆皆 `QUEUED`(不得被新分類誤吃)。
- AC-09-4:token 端點 Transport 直接 reject(模擬 timeout)→ `QUEUED`。
- AC-09-5:token 端點回 400 → `FAILED`(既有行為不變)。
- AC-09-6:`getToken()` 單獨呼叫、遇 200 + 非 OAuth body 時擲出的錯誤,`instanceof ErpHttpError` 仍為 true(或具備所選的判別欄位),且可被明確辨識為 malformed。
- AC-09-7:inspection 端點本身回 200 但 body 缺 `inspectionId` → 仍是 `SYNCED`、`inspectionId` 為 `undefined`(本條不擴大到 inspection 回應)。

## 3. A-04 — `measurement.ts` 退化守衛改用 `Number.isFinite`(`src/engines/measurement.ts`)

### 3.1 問題

`pxPerMm` 的註解寫「避免 Infinity/NaN 流入下游量測與 CSV」,但守衛是 `<= 0`——對 `NaN` 與 `Infinity` 皆為 false,兩者原樣穿透。`src/engines/gate.ts` 對同一問題一律用 `Number.isFinite`;同一 repo 兩套標準,而較鬆的那套的註解卻宣稱自己做到了嚴的那套。

### 3.2 功能描述

把 `measurement.ts` 內所有「退化輸入防護」的守衛改成先驗有限性,再驗正負,與 `gate.ts` 對齊。已知位置至少:

- `pxPerMm`(約 :31)的兩個條件 `scale.resolvedPx <= 0`、`scale.nominalMm <= 0`
- `quietZoneX`(約 :69)的 `xDimPixels <= 0`

**實作前請全檔掃一次**,凡是拿外部數值做比較而未驗有限性的分支都一併收斂(例如 `xDimMm` / `moduleSizeMm` 的 `narrowestElementPx` / `modulePixels` 若為非有限值,輸出必須是 0 而不是 `NaN`)。

判準統一為:任一輸入不是有限數(`Number.isFinite === false`),或不符合原本的正值要求,一律回退到原本的退化輸出值 `0`。**退化輸出值仍是 0,不改成別的數字,也不改成擲錯。**

### 3.3 輸入 / 輸出定義(預期行為表)

| 函式 | 輸入 | 改動後輸出 |
|---|---|---|
| `pxPerMm` | `{resolvedPx: 300, nominalMm: 85.6}` | `300/85.6`(與改動前逐位相同) |
| `pxPerMm` | `resolvedPx = NaN` | `0` |
| `pxPerMm` | `nominalMm = NaN` | `0` |
| `pxPerMm` | `resolvedPx = Infinity` | `0` |
| `pxPerMm` | `nominalMm = Infinity` | `0` |
| `pxPerMm` | `resolvedPx = -Infinity` / `0` / 負值 | `0`(既有行為) |
| `gsd` | 上述任一退化情形 | `0` |
| `xDimMm` | `narrowestElementPx = NaN` 或 `Infinity` | `0` |
| `xDimMm` | 正常值 | 與改動前逐位相同 |
| `moduleSizeMm` | 同 `xDimMm` | 同上 |
| `quietZoneX` | `xDimPixels = NaN` / `Infinity` | `0` |
| `quietZoneX` | `quietZonePixels = NaN` / `Infinity` | `0` |
| `quietZoneX` | 正常值 | 與改動前逐位相同 |
| `barWidthGainMm` | 任一輸入非有限 | `0` |

同時**更新該處的正體中文註解**,讓文字與行為一致(現行註解宣稱擋了 Infinity/NaN,實際沒有——改完後那句話才成立)。

### 3.4 `csv.ts:formatNumber` 的連帶收斂

`src/export/csv.ts` 的 `formatNumber` 對非有限值 `return String(n)`,會讓儲存格出現字面的 `NaN` / `Infinity`。本輪**一併收斂**:

- 非有限值(`NaN`、`Infinity`、`-Infinity`)的輸出字串一律為**空字串 `""`**。理由:CSV 消費端(Excel / BI)把空白視為「無量測值」,比字面 `NaN` 安全,也與 `escapeField` 對 `null`/`undefined` 已有的空字串慣例一致。
- 有限值的輸出字串與改動前**逐字元相同**(仍走 `toPrecision(10)` 收斂浮點雜訊)。
- 欄位順序、引號跳脫、公式注入防護(`= + - @ Tab CR` 前置單引號)一律不動。

### 3.5 驗收標準

- AC-04-1:§3.3 表格每一列都有對應斷言,全數成立。
- AC-04-2:**重演稽核情境**——以 `resolvedPx = NaN` 的 `ScaleReference` 走 `pxPerMm` → `gsd` → `xDimMm` → `quietZoneX`,斷言四個輸出皆為 `0`,無任何 `NaN` 外洩。
- AC-04-3:`formatNumber` 經公開匯出路徑(`toCsv` 之類)驗證:含非有限量測值的 session 產出的 CSV,對應儲存格為空字串,列的欄位數不變、逗號數不變。
- AC-04-4:既有 `tests/measurement.test.ts` 與 `tests/csv.test.ts` **一字不改、全數通過**,作為「正常路徑零變更」的證據。
- AC-04-5:所有 `WASHBOARD_AMP_RATIO_FLOOR` 等常數值未被更動(可用既有 `gate-spec-sync` / `rules-spec-sync` 測試作為佐證)。

## 4. A-11 — 釘住 `SCANLINE_SPREAD_HINT` 與 `spreadHint` 行為(只新增 `tests/`)

### 4.1 問題

`demo/imgproc.js` 匯出的 `SCANLINE_SPREAD_HINT = 1.0` 是稽核 A-06(結果頁可同時顯示 F 級與全 A 參數)**唯一的緩解機制**,卻在 241 個測試中一次都沒被提及。使用處在 `explainGrade` 的 `spreadHint`。

### 4.2 交付物

**純測試**。在 `tests/` 內(沿用既有 `tests/imgproc.test.ts` 的 import 慣例,`// @ts-expect-error` 註解照抄周圍寫法)新增測試,**不得修改 `demo/imgproc.js` 一個字元**。

### 4.3 待釘住的行為

`explainGrade` 回傳的 `spread` 與 `spreadHint` 定義:

- `spread` = 有限 `scanlineScores` 的 `max − min`;有效分數少於 2 筆時為 `null`。
- `spreadHint` 為**非空提示字串** ⟺ `spread !== null && spread > SCANLINE_SPREAD_HINT`(**嚴格大於**);否則為空字串 `""`。
- 提示字串的措辭指向「重拍」(拍攝條件不穩),不得指向「這批印壞了」。
- `spreadHint` **不參與任何評級**:同一組 `parameters` 下,`overallScore`、`limiting`、`rule` 不因 `spread` 改變。

### 4.4 驗收標準(邊界全覆蓋)

- AC-11-1:`SCANLINE_SPREAD_HINT === 1.0`(直接 import 常數斷言其值,任何人改動它都會紅)。
- AC-11-2:`spread` **剛好等於** 門檻(如 `scanlineScores: [2.0, 3.0]` → spread 1.0)→ `spreadHint === ""`(嚴格大於,等於不觸發)。
- AC-11-3:`spread` **略高於**門檻(如 `[2.0, 3.01]`)→ `spreadHint` 非空字串。
- AC-11-4:`spread` **略低於**門檻(如 `[2.0, 2.99]`)→ `spreadHint === ""`。
- AC-11-5:`spread` 為 `null`(`scanlineScores` 為 `[]`、只有 1 筆、或未提供)→ `spreadHint === ""` 且 `spread === null`,不得擲錯。
- AC-11-6:`scanlineScores` 含 `NaN` / `Infinity` / 非數字項 → 被濾除後再算 `spread`;濾除後不足 2 筆時 `spread === null`。
- AC-11-7:提示字串內容包含「重拍」字樣(釘住措辭方向,避免日後被改成怪罪印刷)。
- AC-11-8:`spreadHint` 觸發與否,`explainGrade(...).limiting` 與 `.rule` 完全相同(證明它不參與評級)。
- AC-11-9:`lines` 等於有效分數筆數。
