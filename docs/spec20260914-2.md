## 1. 功能描述

### 1.1 A-10:`shotGate` 的光度四項改量 ROI

**現況(病灶)**:`inspectReal` 在 `const shotQ = measureQuality(small, small.width, small.height)` 對**整張降取樣照片**
算 varLap / glare / wash / wb,而 `src/engines/gate.ts:30` 的定義白紙黑字是 `Laplacian variance over the ROI`。
分母是整個畫面 ⇒ 使用者站遠一點就能任意稀釋:條碼佔 9% 畫面時,失焦條碼配銳利印刷背景量到 30247(對焦 OK),
ROI 只有 58(對焦 FAIL);條碼整片被眩光打白,ROI 眩光 100% 卻因全幀佔比 1%–4% 被判 OK/WARN。
**這不是門檻調校問題,是量錯對象。**

**修法(零門檻改動)**:同一支 `measureQuality`,改餵「ROI 裁切後的影像」。
ROI 取用**與光度量測基底一致的那一塊** —— 即未矯正的 `roiFull`(對應 `rg` / `pmRoi` 的取像範圍),
不是矯正後的正射影像:光度基底的分流理由(稽核裁示 D3 · QUAD-04 / IMG-07)不因本輪而改變。

### 1.2 A-01:「全部 OK」改三態呈現

**現況(病灶)**:`shotGate` 只列非 OK 項,全綠寫死 `"全部 OK"` → PDF 印「本張閘門 全部 OK」。
於是「真的量過且通過」與「因承接放行假值而恆綠」完全無法區分。最強一支:
`state.gate.pxm` 全檔唯一寫入點在 1D 的 `if (g1.modulePx)` 內,2D(QR / DataMatrix)從不寫入,
讀到的永遠是 `resetPreviewGeometry()` 的硬寫值 `9` ⇒ `9 >= 8` ⇒ 解析度**每一張、無例外**為 OK。
同一份 PDF 上一行誠實地不印 px/module,下一行卻隱含斷言解析度通過 —— 自相矛盾,且正卡在實機驗收路徑上。

**修法(零門檻改動)**:改三態呈現 —— **量過且 OK / 量過且非 OK / 未量測**。判準全用現成資訊,不新增量測:

| 檢查項 | 判定「有量過」的依據 | 未量測時的情形 |
|---|---|---|
| `focus` / `glare` / `washboard` / `whiteBalance` | 恆為已量測(本輪起量在本張照片的 ROI 上) | 不會發生 |
| `resolution` | 本張是否真的量到 px/module(即 1D 且 `g1.modulePx` 為真) | 2D **恆為未量測**;1D 量不到掃描線時亦為未量測 |
| `perspective` | `tilt.source !== "none"` | 四角不可得(多數 1D)→ 未量測 |
| `picket` | 是否解碼成功(`!!zx`,`state.gate.picket` 唯二寫入點都在 `if (zx)` 內) | 未解碼 → 未量測 |
| `scaleRef` | 維持現行:**不納入本張閘門敘述**(現況已 `c.key !== "scaleRef"` 排除) | — |

「未量測」的項目**不得**被計入 OK,也不得被講成非 OK —— 它是第三態,要在字面上讀得出來。

### 1.3 交互作用:取幀新鮮度(`assessShotFreshness`)必須一起處理

`assessShotFreshness` 拿 `previewGate` 與 `shotGate` 的**對焦 / 眩光互比**,判斷「預覽是好的、照片卻不是」;
`gateOn` 的註解明寫「讓兩組閘門只在光度四項上有差別,其餘輸入完全相同 —— 對照才乾淨」。
若 A-10 只把 `shotQ` 改吃 ROI 而 `previewQ` 仍是全幀,這個對照就從「同尺度比光度」變成「ROI 比全幀」,
兩者本質不同(條碼區域 vs 整張畫面的 varLap / 眩光占比),新鮮度會開始無差別誤報或漏報 ——
而 2026-08-06(`report20260806-1.md`)已實證 varLap 比值在靜止圖上就會擺動 1%–137%,不可當硬判準。

**本規格採方案 (b):新鮮度改用「同為全幀的兩個量」比,與本張閘門脫鉤。**

- 保留現行的全幀快門讀數(本規格稱 `shotQFull`,即今日的 `shotQ`,計算方式一字不改),
  以及由它評出的 `shotGateFull`;**新鮮度只吃這一對**(`previewGate` vs `shotGateFull`),
  故 2026-08-06 建立的判準**行為完全不變**,不引入任何新的失準來源。
- 新增 `shotQRoi` / `shotGateRoi`,**只供「本張閘門」報告與三態呈現使用**。
- 兩者的差別必須在程式註解裡寫明:新鮮度問的是「預覽到快門之間有沒有劣化」(相對、需同尺度),
  本張閘門問的是「這張照片的條碼區域拍得好不好」(絕對、必須對 ROI)。**同一支 `measureQuality`,不同取樣對象。**

為何不採 (a):預覽階段不解碼、ROI 未知,稽核已認定情有可原,屬規劃書 §6.3 待辦。
為何不採 (c):停用會讓已運作且有價值的判定消失;既然只要保留全幀那一對就能維持原判準,沒有停用的理由。

成本(必須寫進程式註解):每次快門多跑一次 `measureQuality`(320 寬縮圖 + 一次 Laplacian),
相對於同一路徑上的解碼與 4M 像素 ROI 量測可忽略。

## 2. 輸入 / 輸出定義

### 2.1 新增:ROI 裁切影像取得(`demo/mobile.html`)

```
roiCanvasOf(photo, roi) → canvas
```
- **輸入**:`photo`(快門照 canvas)、`roi`(全解析度座標的 `{x0,y0,x1,y1}`,即 `roiFull`)。
- **輸出**:一張只含該 ROI 區域的 canvas,寬高為 ROI 的實際寬高(夾回畫布範圍、保底 1×1;
  座標夾回沿用既有純函式 `scaleRoi(roi, 1, photo.width, photo.height)`,不自己寫夾回邏輯)。
- **邏輯**:`drawImage(photo, x0, y0, w, h, 0, 0, w, h)`。不做任何縮放 ——
  `measureQuality` 內部自己會縮到 320 寬,在這裡先縮一次等於改變取樣鏈。
- **為什麼要有具名函式**:demo 層沒有執行期測試,守門測試只能讀原始碼;
  有具名函式才能把「本張閘門吃的是 ROI」釘成可斷言的結構,而不是一串認不出來的 inline 參數。

### 2.2 新增:本張閘門三態敘述(**純函式,放 `demo/imgproc.js`**)

```
summarizeShotGate({ checks, measured, labels }) → string
```
- **輸入**
  - `checks`:`gate.report.checks` 形狀的陣列,元素為 `{ key, status }`,`status ∈ {"OK","WARN","FAIL"}`。
  - `measured`:`{ [key]: boolean }`,對應 §1.2 表格的「有量過」判定;**鍵不存在視為已量測**
    (光度四項不必逐一列出,避免新增檢查項時靜默落入「未量測」)。
  - `labels`:`{ [key]: string }` 檢查項中文標籤(呼叫端傳 `CHECK_LABEL`,純函式不自帶 UI 字典)。
- **輸出**:單行字串,供結果頁與 PDF 直接顯示。
- **邏輯與格式**(下列字面為驗收對象):
  1. 排除 `key === "scaleRef"`(沿用現況)。
  2. 分三組:`未量測`(`measured[key] === false`)、`非 OK`(已量測且 `status !== "OK"`)、`OK`(已量測且 `status === "OK"`)。
  3. 依序輸出、以 `` · `` 串接,組內以 `、` 串接:
     - 非 OK 組:`` 未過 對焦 FAIL、眩光 WARN ``
     - 未量測組:`` 未量測 解析度、透視 ``
     - OK 組:`` 已量測通過 N 項 ``(N 為已量測且 OK 的項數)
  4. 已量測且全數 OK、且沒有未量測項時,輸出 `` 已量測通過 N 項 ``(**不得出現「全部 OK」字樣**)。
  5. 全部項目都未量測(理論上不會發生)時輸出 `` 未量測 …列出所有項 ``,不得輸出空字串。
- **為什麼放 `demo/imgproc.js`**:那是本專案唯一「demo 層但可在 Node 直接測」的位置
  (`tests/imgproc.test.ts` 既有慣例)。寫進 HTML 的 inline JS 就只能用字串比對守門,抓不到邏輯回歸。

### 2.3 異動:`inspectReal` 內的閘門評估

| 變數 | 來源 | 用途 | 本輪 |
|---|---|---|---|
| `previewQ` | 快門前最後一次預覽讀數(全幀) | 新鮮度對照組 | 不變 |
| `shotQFull` | `measureQuality(small, …)`(全幀) | **僅**新鮮度 | 由 `shotQ` 更名,計算不變 |
| `shotQRoi` | `measureQuality(roiCanvasOf(photo, roiFull), …)` | **僅**本張閘門 | 新增 |
| `previewGate` / `shotGateFull` | `gateOn(previewQ)` / `gateOn(shotQFull)` | `assessShotFreshness` 的四個布林 | 語意不變 |
| `shotGateRoi` | `gateOn(shotQRoi)` | `lastShotInfo.shotGate` 三態敘述 | 新增 |

`gateOn` 的其餘輸入(`symbolDetected` / 幾何三項 / `scaleRefDetected` / `fluteType`)一律維持現狀,不得調整。

`shotQRoi` 必須在 `roiFull` 算出之後才求值(現況 `shotQ` 在 ROI 之前,順序必須調整);
`shotGateRoi` 與三態敘述必須在 `applyTilt` 與 1D / 2D 分支跑完之後才組,否則 `tilt.source` 與 px/module 量測旗標尚未成形。

### 2.4 異動:量測旗標(供 §1.2 判定)

`inspectReal` 需在函式層宣告一個旗標,於真正量到 px/module 的**同一個 `if (g1.modulePx)` 區塊內**設為真:

```
let pxmMeasured = false;   // 本張是否真的量到 px/module(2D 恆 false → 解析度呈現為「未量測」)
```

其餘兩項直接用現成值:`perspective` 看 `tilt.source !== "none"`,`picket` 看 `!!zx`。

### 2.5 異動:取幀資訊欄位

- `lastShotInfo.shotGate`:內容改為 §2.2 的三態字串(欄位名與 PDF 的 `"本張閘門 " + shot.shotGate` 行不變)。
- 新增 `lastShotInfo.shotGateBase = "ROI(裁切後)"`:讓 PDF 明細講得出這張報告的閘門量在哪裡 ——
  沒有這一欄,新舊報告在紙上長得一樣卻不可互比(見 §5)。
- `lastShotInfo.shotTiming` / `staleShot`:不變(仍由全幀那一對產生)。

| E2 | **退化 ROI**(寬或高 < 1 px,或座標落在畫布外) | `roiCanvasOf` 經 `scaleRoi` 夾回並保底 1×1,不得丟例外;`measureQuality` 在 1×1 上的讀數照常進閘門(不特別處理,但不得當掉) |
| E3 | **1D 走矯正**(`plan.useRectified` 為真) | 本張閘門仍量**未矯正的 `roiFull`** —— 與 `roiPhotometric` 的光度基底(`pmRoi`)一致;不得改吃正射影像 |
| E4 | **2D**(QR / DataMatrix) | `resolution` 恆為未量測;`perspective` 視 `tilt.source` 而定;`px / module` 欄位維持現況留白(`renderShotRead` 不變) |
| E5 | **1D 但掃描線全滅**(`scanlineCount` 為 0、`g1.modulePx` 不可得) | `pxmMeasured` 為 false → `resolution` 未量測;不得沿用上一張的值,也不得因為 `state.gate.pxm` 仍是 9 而印 OK |
| E6 | **模擬檢驗(無相機)** | `lastShotInfo` 為 null,整段不執行 —— 現行 `if (lastShotInfo)` 保護維持,不得編造取幀資訊 |
| E7 | **取幀新鮮度** | 仍由 `previewGate` vs `shotGateFull` 產生;`shotTiming` / `staleShot` 的文字與門檻一字不動 |
| E8 | **ROI 光度 FAIL 但全幀 OK**(A-10 的兩個 false-OK 情境) | 本張閘門如實印出「未過 對焦 FAIL」;**快門仍不會被鎖死**(§0.1),新鮮度也可能同時報「預覽好、照片差」—— 兩者並存是預期,不是矛盾 |
| E9 | **檢查項未來新增**(gate.ts 多一項) | `measured` 未列的鍵視為已量測 → 新項落入 OK / 非 OK 兩態,不會被靜默算成「未量測」而消失 |

## 5. 已知且被接受的成本:修改前後的檢驗紀錄不可互比

本輪**會改變「本張閘門」報告的內容**,而且改的是量測對象與敘述語意兩件事:

- 舊紀錄的「本張閘門」光度四項量的是**全幀**,新紀錄量的是**ROI**。數值與判定不在同一個尺度上。
- 舊紀錄的「全部 OK」包含**從未量過**的項目;新紀錄把未量測項獨立列出。
  同一張照片在改動前後可能一邊印「全部 OK」、一邊印「未過 對焦 FAIL · 未量測 解析度、透視」——
  **不是其中一份壞掉,是舊的那份在說謊。**

依規劃書 §6.1 的精神(量測條件變動時,跨版本讀數不可互比):
**2026-09-14 之前產出的檢驗紀錄與 PDF,其「本張閘門」一欄不得與本輪之後的紀錄並列比較。**
`lastShotInfo.shotGateBase`(§2.5)就是為此存在的版本標記 —— 有這一欄的是新語意,沒有的是舊語意。
分級、允收判定與所有門檻均未變動,故**除「本張閘門」一欄外**的紀錄仍可互比。
