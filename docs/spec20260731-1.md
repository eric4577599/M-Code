## 1. 現況與問題

以下數據皆為 2026-07-31 實際查證程式碼所得,非推測。
**本節記錄的是改動前(HEAD `e0c4675`)的狀態**,保留為問題陳述的原始依據;階段 ①②
實作後的實況見 §3.1 的「實作實況」段與 §4 的狀態欄。

### 1.1 影像處理層的位置

`demo/imgproc.js`(288 行)是唯一的像素層,匯出 12 個純函式,不碰 DOM,由 `tests/imgproc.test.ts` 在 Node 直接測。核心庫 `src/` 刻意不做影像處理 —— `src/engines/gate.ts` 檔頭明載「數值由前端注入」。**本規格不改動這條架構界線。**

像素只在兩處被讀取:

| 路徑 | 頻率 | 尺寸 | 做的事 |
|---|---|---|---|
| 即時預覽迴圈 `measureFrame` | 500 ms | 320 px 寬 | `varLap` / `glare` / `wb` / `washboard` 四項全域量測 |
| 快門後單次 `inspectReal` | 每張一次 | ≤1024 px 寬 | ZXing 解碼 → ROI → 光度與幾何量測 → 分級 |

### 1.2 八項閘門檢查的實況(`src/engines/gate.ts`)

| 檢查 | 門檻 | 即時可算 | 資料來源 |
|---|---|---|---|
| focus | ≥120 否則 FAIL | 是 | `varianceOfLaplacian` |
| glare | ≤1% OK / 1–4% WARN / >4% FAIL | 是 | `glareRatio` |
| washboard | ≤0.08 / 0.15 | 是 | `washboardAmpRatio` |
| whiteBalance | ≤5% 建議燈,永不鎖快門 | 是 | `grayWorldWbDeviation` |
| scaleRef | 偵測到 / 否 | **未實作**,硬寫 `false` | — |
| picket | ≤10° / 25° | 否,拍後才有 | ZXing 定位點 |
| **perspective** | **≤5° 否則 FAIL** | 否,拍後才有 | 臂長差粗估 |
| resolution | `gsd≤0.20` 且 `pxPerModule≥8` | 否,拍後才有 | `roi1DGeometry` |

### 1.3 問題一:透視閘門形同虛設

`demo/mobile.html:628` 在每一幀即時迴圈把幾何項還原為安全放行值:

```js
state.gate.picket = 0; state.gate.tilt = 0; state.gate.pxm = 9;
```

理由本身是對的(避免上一張的殘留值鎖死下一張預覽),但結果是**「透視 ≤5° 否則 FAIL」這道閘門在按下快門之前從未擋過任何人**。

而拍完之後的 `tiltDeg` 也只是粗代理(`demo/imgproc.js:253`):

```js
const lenDev = Math.abs(l1 - l2) / Math.max(l1, l2);
const tiltDeg = (Math.asin(Math.min(1, lenDev)) * 180) / Math.PI / 2;
```

這是「兩條臂不一樣長 ⇒ 大概斜了」,不是真實傾角。

### 1.4 問題二:傾斜污染 DEC 量測

`roi1DGeometry`(`demo/imgproc.js:201`)以「最窄 run 的 10 百分位」當模組寬,再算各 run 對模組整數倍的偏差 `maxWidthDeviation`。傾斜拍攝時近端模組寬、遠端窄,此偏差被記為印刷缺陷 —— **把拍攝問題誤判成品質問題**,這是相對篩檢工具最不該犯的錯。

### 1.5 問題三:解析度從未被偵測,且被硬砍

| 層級 | 現行值 | 位置 | 怎麼決定的 |
|---|---|---|---|
| 相機串流 | 瀏覽器預設 | `mobile.html:576` | 只帶 `facingMode`,無解析度約束 |
| 即時量測 | 320 px 寬 | `mobile.html:615` | 寫死(合理) |
| **快門分析影像** | **≤1024 px 寬** | `mobile.html:682` | `Math.min(1024, videoWidth)` 硬砍 |
| 縮圖 / 報告原圖 | 320 px 寬 | `mobile.html:471` | 寫死(合理) |
| `gsdMmPerPx` | **0.12** | `mobile.html:402` | **硬寫的假值** |

規劃書 A4.3 要求每模組 5–10 px、ITF-14 直印 100%(X≈1.016 mm)需 GSD 0.10–0.20 mm/px。以視野寬度 300 mm 計算(ITF-14 含靜區實體寬約 100–145 mm,旁邊還需並排比例尺卡,這是實務下限):

| 影像寬 | 視野 | GSD (mm/px) | X=1.016mm | X=0.495mm | resolution 判定 |
|---|---|---|---|---|---|
| 640 | 300 mm | 0.469 | 2.2 px | 1.1 px | FAIL |
| 1024 | 300 mm | 0.293 | 3.5 px | 1.7 px | FAIL |
| 1024 | 150 mm | 0.146 | 6.9 px | 3.4 px | WARN |
| 4032 | 300 mm | 0.074 | 13.7 px | 6.7 px | OK / WARN |
| 4032 | 150 mm | 0.037 | 27.3 px | 13.3 px | OK |

**結論:正常拍攝距離下,1024 px 永遠過不了 `pxPerModule ≥ 8`。**

現在看不出問題,是因為兩個假數字互相掩護:`gsdMmPerPx` 硬寫 0.12、即時迴圈把 `pxm` 塞預設值 9,這道檢查因此一路綠燈。

**改動後仍有一個假數字(2026-07-31 回寫,依程式碼查證)。** 階段 ② 只拆掉了兩個假數字中的
一個 —— `gsdMmPerPx` 的 0.12 已移除(`evalGate()` 恆傳 `null`),但 `pxm = 9` **原封不動**:

| 時點 | `state.gate.pxm` | `resolution` 判定 |
|---|---|---|
| 即時預覽(每 500 ms `measureFrame()`) | **硬寫 9**(與 `picket=0`、`tilt=0` 同一行還原) | 走「GSD 不可得」分支,9 ≥ 8 → **恆 OK** |
| 快門後 `inspectReal()` | `if (g1.modulePx) state.gate.pxm = g1.modulePx` 回填真值 | ~~依真實 `pxPerModule` 判定,可能 WARN/FAIL~~ **見下方更正** |
| 下一次 `measureFrame()`(≤500 ms 後) | 又被還原成 9 | 回到恆 OK |

> **⚠️ 上表第二列已於 2026-08-05 更正(稽核 IMG-01)。** 原文寫「依真實 `pxPerModule` 判定,
> 可能 WARN/FAIL」**從來沒有發生過**:回填真值之後、`recompute()` 之前,`inspect()` 的
> `finally` 會先呼叫 `resetPreviewGeometry()` 把 `picket`/`tilt`/`pxm` 蓋回 `0/0/9`,
> 而全檔 `evaluateGate` 的呼叫點只有 `evalGate()` 一處(吃的恆為預覽值)。
> 也就是說**八項閘門從未對「實際被分級的那張影像」跑過一次**,不只是「短暫存在」而已。
> 這一列是規格自己過期的第三個案例,成因與前兩次相同:改程式的人沒回來改規格。
>
> **2026-08-05 的處置(裁示 D5③):** 在 `inspectReal` 補跑一次 `evaluateGate`,
> 結果只寫進 `lastShotInfo.shotGate` → `scans` → PDF 明細的「本張閘門」欄。
> **刻意不鎖快門、不改分級、不碰任何門檻** —— 事後鎖死會閃出一則活不過半秒的判定
> (原 `finally` 註解的顧慮成立),而分級與閘門是兩套語意不得互相覆寫。
> 現在報告第一次講得出「這張照片的實際拍攝品質」,但它仍然**不參與判定**。

也就是說**真實 `pxPerModule` 過去只在快門後到下一次量測之間短暫存在且無人讀取**,
快門前的 `resolution` 檢查與改動前完全一樣、從未擋過任何人。這與 §1.3 的透視閘門是同一個病灶(同一行程式碼),
根因不在 `gate.ts` 而在「幾何量測拍後才有」,解法是 §6.3 已列的「picket 與 px/module 燈號
拍攝前即時化」,**不在本規格範圍**。故 §2 的 **G2 僅部分成立**:誠實化只做到了 GSD 這半邊,
`pxPerModule` 那半邊在即時迴圈仍是假值。

### 1.6 問題四:無任何補光控制

全 repo 查無 `torch` / `applyConstraints` / `getCapabilities` / `ImageCapture` 相關程式碼。`getUserMedia` 僅帶 `facingMode`(`mobile.html:576`)。低照度現場(倉庫、夜班、印刷機旁)只能靠環境光。

### 1.7 問題五:GSD 假值造成的誠實性缺陷

規劃書 A4.5 明載:無實體基準則只有像素、量不出 mm,**故基準物為必要非選配**。現況是 `scaleRef` 硬寫 `false`(誠實),但 `gsdMmPerPx` 卻填 0.12 讓 `resolution` 檢查看似通過(不誠實)。兩者矛盾。

## 2. 目標

做完之後,以下敘述必須為真且可驗收:

- **G1** 拍攝分析影像的寬度不再被 1024 px 上限限制,而是取自裝置實際能力,並在結果中誠實記錄「請求值 / 實拿值」。⚠️ **僅部分成立** —— 走第三層(保底 `drawImage`)的裝置寬度仍被預覽的 1280 px 封住,見 §3.1 與 §6.5 決策 ①。

- **G3** 解碼成功且四角可得時,量測改吃梯形矯正後的正射 ROI,`maxWidthDeviation` 不再被拍攝傾斜污染。
  ⚠️ **僅對「四角皆實測」的符號別成立(2026-08-03 階段 ④ 接線後回寫,2026-08-04 更新)** ——
  DataMatrix(ZXing 給四點)走得到;**QR 只有 v≥2 走得到**(由 alignment pattern 還原真四角,

- **G4** `perspectiveTiltDeg` 改由單應矩陣推導,取代臂長差代理;`gate.ts` 的 ≤5° 門檻數值不變。
  ⚠️ **僅部分成立(2026-08-03,2026-08-04 更新)** —— 條件有二:① 四角皆實測

  任一不成立即依 2026-08-03 裁示退回臂長差代理值並在結果頁標註;兩者皆無則標「未量測」。
  詳見 §6.5 決策 ②。

## 3. 設計

### 3.1 提案 A — 解析度偵測與取幀

**三段式取得。** 為什麼不一開口就要 4K:一開始就要求最高解析度容易觸發 `OverconstrainedError`,且未授權前讀不到完整 capabilities。

1. 先用現行寬鬆約束開串流,取得權限與能力表。
2. 讀 `track.getCapabilities()` 的 `width.max` / `height.max`;Android Chrome 另可用 `ImageCapture.getPhotoCapabilities()` 取得**照片**解析度上限(通常遠高於視訊,如 4032×3024 對 1920×1080)。挑選邏輯抽成**純函式 `pickBestResolution(caps)`**,才測得到。
3. 預覽與拍攝分離:預覽維持 1280×720,只在按下快門的瞬間取全解析度。

**為什麼預覽不拉高:** 串流拉到 4K 會掉幀、發燙、耗電,而即時迴圈本來就降到 320 px,拉高零收益。

**快門瞬間的三層降級:**

| 層 | 條件 | 做法 |
|---|---|---|
| 1 | 支援 `ImageCapture` | `new ImageCapture(track).takePhoto()` —— 直接取照片解析度,不動預覽串流 |
| 2 | 支援 `applyConstraints` 但無 `ImageCapture` | 暫時升壓 → 等 1–2 幀重新協商 → `drawImage` → 降回 720p |
| 3 | 其他(iOS Safari) | **保底沿用預覽解析度**:直接對預覽 `video` 做 `drawImage`,寬度即預覽協商到的寬 |

**實作實況(2026-07-31,已依程式碼回寫):** 本節原文寫第三層是「開串流時帶
`width:{ideal:4096}`,回讀 `getSettings()` 看實際拿到多少」,**這一段沒有實作**,原因是它
與同一節「預覽維持 1280×720 不要拉高」直接衝突 —— `getUserMedia` 端固定帶
`width:{ideal:1280}, height:{ideal:720}`(`mobile.html` 的 `PREVIEW_W/PREVIEW_H`),
第三層 `captureViaDrawImage()` 只是對這條預覽串流 `drawImage`。第三層的實際語意因此是
**「保底沿用預覽解析度」**:相對改動前唯一的進步是拿掉了 `Math.min(1024, videoWidth)`
硬砍,但上限被預覽解析度封住,通常就是 1280 px。

**兩套「層」不是同一件事,不要混用:**

| 名稱 | 出處 | 分層依據 | 取值 |
|---|---|---|---|
| `tier` 1/2/3 | 純函式 `pickBestResolution(caps, photoCaps)` | 解析度**來源** | 1 photo / 2 track / 3 fallback(4096×4096) |
| `L1/L2/L3` | `capturePhoto()` | 快門**取幀路徑** | L1 ImageCapture / L2 applyConstraints 升壓 / L3 drawImage |

兩者不一一對應:`tier` 3 的 4096×4096 只是「請求 ideal 讓瀏覽器自己 clamp」的請求值,
裝置若支援 `applyConstraints`,這個值仍會被 **L2** 拿去做快門瞬間升壓(升壓後隨即降回
720p);**只有 L1、L2 皆不可用或失敗時才會落到 L3**。因此「iOS Safari 走第三層」是
規格原文的假設,**實機實際走 L2 還是 L3 未驗證**(Safari 不支援 `ImageCapture` 是已知的,
但它的 `getCapabilities()` / `applyConstraints` 行為未實測)。

**`widthOnly` 尚未接線(記錄事實):** `pickBestResolution` 回傳的 `widthOnly`(tier 1 為
`false`、tier 2/3 為 `true`,理由見該函式 JSDoc:`caps.width.max` 與 `caps.height.max` 來自
兩個獨立區間、不保證同一模式;4096×4096 是 1:1 假比例)目前**只被單元測試鎖住**,
`captureViaConstraints()` 仍寬高一起下 `ideal`。接線與否待階段 ① 實機驗收後再定。

**未決:** 若 iOS Safari 實際落在 L3,其分析影像寬度會鎖在預覽的 1280 px,**§2 的 G1
「寬度取自裝置實際能力」對這類裝置不成立**。三個選項與裁示狀態見 **§6.5**,本規格不預設答案。

**記憶體護欄(硬性):** 4032×3024 的 `getImageData` 是 48 MB RGBA,`toGray` 再吃 12 MB;iOS Safari 的 canvas 有面積上限,舊機會被系統回收分頁。因此:

- 全解析度**只用於 ROI**,不對全張跑量測。
- 流程改為:降取樣版解碼定位 ROI → ROI 座標放大回全解析度 → 只對 ROI 取 `getImageData`。
- `washboardAmpRatio` 等全域統計**繼續跑 320 px 版**,它量的是低頻週期,不需要高解析度。

### 3.2 提案 A' — GSD 誠實化(`src/engines/gate.ts`)

`classifyResolution` 增加「GSD 不可得」分支。**設計上比照既有前例** `classifyWashboard` 對 `fluteType === "NONE"` 的處理(回傳 N/A、不套固定門檻、value 仍回傳原始值供除錯)。

- `gsdMmPerPx` 為 `null` / `undefined` 時,僅以 `pxPerModule` 判定(`<5` FAIL、`<8` WARN、否則 OK),`threshold` 字串標明 GSD 不可得。
- **不放寬** `pxPerModule ≥ 8` 或 `gsd ≤ 0.20`。這兩個門檻來自規格 A4.3,現在過不了是輸入不夠好,不是門檻太嚴。
- 呼叫端 `mobile.html:402` 移除硬寫的 `0.12`。

此為 `src/` 改動,依專案 DoD **必須附 vitest**。

### 3.3 提案 B — 梯形矯正

全部為純函式,加在 `demo/imgproc.js`,由 `tests/imgproc.test.ts` 測。`src/` 不動 —— 矯正後 `tiltDeg` 仍只是注入給 `gate.ts` 的數字。

**四角來源依符號別分流:**

| 符號別 | ZXing 給的點 | 取四角策略 | 可行性 |
|---|---|---|---|
| QR | **3 或 4** —— v≥2 時 ZXing 會多回一個 **alignment pattern 中心(不是角點)** | 有 alignment(v≥2)→ 由模組座標解出「模組平面 → 影像」的 H,再映回符號真四角;無 alignment(v1)→ 退回 `tr + bl − tl` 補點 | v≥2 拿得到**真透視**;v1 只能補點(推不出傾角,見補點段) |
| DataMatrix | 4 | L 型實邊兩端 + timing 兩端直接對應 | 直接可做 |
| ITF-14 / GS1-128 / CODE128 | 2(掃描線端點) | 沿定位線法向搜尋條端得上下兩線、沿條高帶內插掃描得左右兩線,**四條邊各自獨立擬合**後求交點(`quadFrom1DEdges`) | **2026-08-04 已實作**,合成實測傾角誤差 < 0.04°(見 §5.4d);詳細演算法與門檻見下方「1D 四角偵測」節 |

**補點四角不帶透視資訊(2026-08-03 階段 ④ 接線時實測,原文未預見)。** `tr + bl − tl` 造出來的
四邊形依定義是**平行四邊形**,而平行四邊形映到矩形的單應矩陣是**仿射**的 —— 兩組對邊平行
即消失點在無窮遠、消失線亦在無窮遠,而 `tiltFromHomography` 正是由消失線反推,故
**不論真實傾角多少一律算出 0.00°**。針孔合成實測(400×400 方形、f=900px、距離 833,
繞 X 軸與繞 Y 軸結果完全相同):

| 真實傾角 | 補點與真實第四角的距離 | 真四角推得的傾角 | **補點四角推得的傾角** |
|---|---|---|---|
| 0° | 0.0 px | 0.00° | 0.00° |
| 2° | 7.2 px | 2.00° | **0.00°** |
| 5° | 18.0 px | 5.00° | **0.00°** |
| 25° | 88.2 px | 25.00° | **0.00°** |

0° 是 `gate.ts`「≤5° 否則 FAIL」**最寬鬆的放行值**,這與 §1.3 的即時迴圈 `tilt = 0`、
§1.5 的 `pxm = 9`、`tiltFromHomography` 初版的「焦距不可得回 0」是**同一個病灶**:
用一個能通過型別檢查的假數字讓檢查看起來有在跑,而且**比現行的臂長差代理值更糟**
(代理值至少會隨傾斜變大)。故:

- `quadFromZxingPoints` 回傳 `{ corners, derived }`,`derived` 為 true 即「第四角是推算的」。
- `rectifyPlan` 對 `derived` 一律 `useHomography: false`、`useRectified: false`
  —— 矯正本身也只還原得了旋轉與剪切、還原不了透視,對 2D 的光度/FPD 量測是白付一次
  雙線性內插的模糊代價,故一併不採用。傾角改走臂長差代理值。
- 唯一能讓 QR 拿到真透視的路徑是本表原文的「有 alignment pattern 時改用實測點」。
  **2026-08-03 查證後這條路是通的,已依決策 ③(c) 實作**,見下方 alignment pattern 段。
- 護欄測試:`tests/imgproc.test.ts` 的
  `it("**補點四角恆推出 0° 傾角**:平行四邊形不帶透視資訊,絕不可拿去推傾角")`
  同時斷言真四角推得回真實傾角(對照組,證明失準來自補點而非管線)。

**alignment pattern:另一個方向相反、後果更嚴重的陷阱(2026-08-03 實測)。**
查證 `demo/vendor/zxing.min.js` 的實際行為:ZXing 的 QR Detector 找到 alignment pattern
時會回**四個** result point,但第四個是 **alignment pattern 的中心,不是右下角**。
實測(以 ZXing 自己的 `MultiFormatWriter` 產生 QR 再解碼):

| 內容長度 | result points | 第四點 |
|---|---|---|
| 短(v1,無 alignment) | 3 | — |
| 長(v≥2) | **4** | alignment 中心,模組座標 (N−6.5, N−6.5) |

右下角在 (N−3.5, N−3.5),兩者差約 **3 個模組**。把 alignment 直接當角點餵進
`solveHomography`,解出來的是數值合法、幾何錯誤的矩陣。針孔合成實測
(dimension 25、每模組 12px、f=900、距離 833):

| 真實傾角 | alignment 當角點 | 還原後 | `quadConfidence.ok` |
|---|---|---|---|
| **0°(完全拍正)** | **53.74°** | 0.00° | `true`(擋不住) |
| 5° | 52.55° | 5.00° | `true` |
| 30° | 47.81° | 30.00° | `true` |

53.74° ≫ `gate.ts` 的 ≤5° → **每一張 v≥2 的 QR 都會 FAIL**,現場等於 QR 完全不能用。
方向與補點四角的「恆綠」相反,但同樣是「檢查在跑、量的卻是錯的東西」,而且
`quadConfidence` 的四重把關全程 `ok=true` —— 它是個正常的凸四邊形,擋不住。

**還原方式(`qrQuadFromPoints`)。** 四個點的模組座標全部已知:

| 點 | 模組座標 |
|---|---|
| tl finder 中心 | (3.5, 3.5) |
| tr finder 中心 | (N−3.5, 3.5) |
| bl finder 中心 | (3.5, N−3.5) |
| alignment 中心 | (N−6.5, N−6.5) |

故解出「模組平面 → 影像」的單應矩陣後,把符號真正的四角 (0,0)(N,0)(N,N)(0,N)
映回影像即可。`N`(dimension)由 ZXing 前三個 result point 的
`getEstimatedModuleSize()` 還原,**算法刻意照抄 ZXing 自己的 `computeDimension`**
(兩條中心距 ÷ 模組寬 + 7,再修正到 ≡1 mod 4)—— 它才是決定 alignment 該擺在哪個
模組座標的那一份定義,自己另想一套會在邊界情形跟解碼結果不一致。
拿不到 alignment(v1)或拿不到模組寬時**退回補點並標 `derived`**,不猜 dimension。

註:傾角與「映回哪一個矩形」無關 —— 同一平面上的兩個矩形只差一個仿射,消失線不變。
取符號真四角而非 finder 中心方框,是為了讓矯正輸出涵蓋整個符號(含最外圈模組)。

**`quadFromZxingPoints` 因此必須知道符號別。** 「四個點」對 DataMatrix 是四個角、對 QR
卻是三個角加一個 alignment 中心 —— 同樣的陣列長度、完全不同的幾何意義。
**符號別不明時一律保守標 `derived = true`**:寧可退回代理值,不可拿一組意義不明的點
去解矩陣。

**一維是最硬的一段。** ITF-14 有 bearer bar 可當上下邊界;GS1-128 沒有,只能靠條的上下端點群做直線擬合。**擬合信心不足時誠實退回「不矯正、沿用現行代理值」並在結果標注,不得硬套一個錯的矩陣。**

#### 1D 四角偵測(階段 ⑤,2026-08-04 落地。本段為權威定義,`demo/imgproc.js` 與本段不一致即為缺陷)

**C1(硬性):四條邊必須各自獨立擬合。** 絕不可把下邊取成上邊的平行線,也不可用單一
「條高帶」推對邊 —— 兩組對邊平行 ⇒ 平行四邊形 ⇒ 單應矩陣是仿射 ⇒ 消失線在無窮遠 ⇒
`tiltFromHomography` **不論真實傾角一律回 0.00°**,正是 ≤5° 閘門最寬鬆的放行值(與上方
補點段同一個病灶)。這條禁的是**強制**平行,**不是**禁止結果剛好平行:真的拍正時四條線
本來就近乎平行、傾角本來就是 0°,那是正確答案,不得因此判失敗。

**新增匯出(皆為 `demo/imgproc.js` 的純函式 / 凍結常數):**

| 名稱 | 型態 | 用途 |
|---|---|---|
| `ONE_D_SYMBOLOGIES` | 凍結陣列 `["ITF14","GS1_128","CODE128"]` | 哪些符號別走 1D 偵測。值取自 `src/domain/types.ts` 的 `Symbology`,**不在別處再寫一份字串**;`QR` / `DATAMATRIX` 不在內 |
| `LINE_FIT_LIMITS` | 凍結物件 | 直線擬合與四角求交的門檻,見下方權威表 |
| `fitLineTLS(pts, opts)` | 純函式 | 總體最小平方直線擬合 + MAD 離群剔除 |
| `quadFrom1DEdges(gray, w, h, points, opts)` | 純函式 | 1D 四角偵測主體,**恆回物件、永不 throw、永不代填數字** |

**`fitLineTLS(pts, { madK })` → `{ nx, ny, c, rmsPx, inliers, samples }` 或 `null`。**
直線以**法式** `nx·x + ny·y + c = 0`(`nx² + ny² = 1`)表示。以二階中心矩的**最小特徵向量**
取法向(總體最小平方)—— **不可用 `y = ax + b` 最小平方**,條垂直(符號旋轉 90°)時斜率
發散。第一輪用全部點擬合 → 算殘差 → 以 MAD(`1.4826 × median|r|`)為尺度剔除
`|r| > madK × scale` 的離群點 → 用內點重擬合一次。`rmsPx` 為**內點**殘差 RMS。
**無亂數**(改用 RANSAC 亦須為決定性列舉)。
**尺度下限 0.1 px(實作補充,規格草稿未預見):** 一組近乎完美的點其 MAD 會小到 0.01 px
等級,`madK × MAD` 會把散度只有次像素內插誤差的**完美內點**剔成離群;子像素邊界內插的
解析度約 0.1 px,比它更小的散度是量化不是離群,故尺度不低於 0.1 px。此下限只影響「本來
就很準」的情形,擋不到真離群(真離群殘差是好幾個 px)。

**`quadFrom1DEdges(gray, w, h, points, opts)` 的輸入 / 輸出契約。** 輸入 `gray` / `w` / `h`
是來源灰階與尺寸(與 `points` **同一座標系**,即 `rectifyQuad` 收到的那組);`points` 是
ZXing 的 result points,**只用前兩個有限點**;`opts = { sym, samples, crossSamples }` 皆可
省略(預設取自 `LINE_FIT_LIMITS`)。輸出**恆為物件**:

- 成功 `{ ok: true, corners, source: "1d-edges", fit, metrics, reason: "" }`,`corners` 為
  4 個 `{x, y}` 且**未排序**(交給既有 `orderCornersRaw`)。
- 失敗 `{ ok: false, corners: null, reason: "1D 邊界擬合失敗（…）", fit, metrics }`。
- `fit = { top, bottom, left, right }`,各為 `fitLineTLS` 的輸出或 `null` —— **四條線必須
  各自可讀**,護欄測試要靠它證明上下邊不是同一條的平移。
- `metrics` 全是**實測值**(同名門檻在 `LINE_FIT_LIMITS`,兩者不要混看):
  `minInliers` / `minInlierRatio` / `maxRmsPx` 是四條線中最差的那條、`minCornerAngleDeg`
  是四個相鄰線對中最小的夾角、`barHeightPx` 是條高;**`samples` 的語意是「上下端點取樣
  時成功產出端點對的位置數」**(即演算法 3. 沒有作廢的 `q_i` 個數,上下兩群等長),
  **不含**左右兩條線的掃描線數,也不是 `LINE_FIT_LIMITS.samples`。退回時能算到哪一步就
  填到哪一步,算不到的維持 `null`。

**`quadFrom1DEdges` 演算法(七步,與實作逐字對應):**

1. **定位線與法向。** 取前兩個有限點 `p0`、`p1`,`u = normalize(p1 − p0)`、`n = (−u.y, u.x)`。
   `|p1 − p0| < minLocatorLenPx` 判端點退化,退回。
2. **閾值(帶內 Otsu)。** 以定位線周邊帶(沿 `n` 各取 `searchHalfSpanRatio × |p1 − p0|`、
   沿 `u` 全長)的子影像算 `otsu`,**不用整張 `gray`** —— ROI 外的背景會把閾值拉偏。
   取樣格上限 256×96(格距固定,無亂數)。**兩道對比關**:帶內只有一類(全白 / 全黑)→
   退回;兩類平均差 < `minBandContrast` → 退回,reason 指名對比不足。
   (草稿只寫「Otsu 分不出兩類」,但 Otsu 在單峰直方圖上照樣回得出一個閾值,故補第二關。)
3. **上下端點取樣。** 沿定位線取 `samples` 個位置 `q_i = p0 + u·L·(i + 0.5)/samples`。
   `q_i` 本身不是暗 ⇒ 落在空白/靜區 ⇒ **作廢**(不補值);否則沿 `±n` 逐像素走,以雙線性
   取樣讀灰階,走到**最後一次**「暗 → 亮」的跨越點即該側條端,跨越點**線性內插到子像素**
   (整數量化在 ±1° 判準下會直接吃掉誤差預算)。走出畫面或走滿搜尋半徑仍未跨越 ⇒ 該位置
   作廢,**不得用畫面邊界當條端**。
   **側向追蹤(實作新增,草稿未預見):** 每一步都在 `±trackHalfSpanRatio × L` 內重新對準
   所在暗 run 的中心 —— 繞畫面水平軸傾斜時條在影像中是**會聚**的、並不平行於 `n`,直直
   往上走會走出條外,在 GS1-128(沒有 bearer bar 兜底)上會把條端記錯位置。兩側都搜不到
   亮(例如寬達整個符號的 bearer bar)則維持原偏移,兩種情形都是要的行為。
4. **上下兩條線分別擬合。** 上端點群 → `fitLineTLS`,下端點群 → `fitLineTLS`,
   **兩次獨立呼叫、兩組獨立資料**(C1)。
5. **左右兩條線分別擬合。** 取 `crossSamples` 條掃描線,**每條沿上下兩線做線性內插**:
   第 k 條的每一點都是「該處上下兩線之間走比例 `f = (k+1)/(crossSamples+1)`」的位置。
   **不是平行於定位線的直線(草稿原文的做法,已被實測推翻):** 透視下上下兩線會聚,
   一條平行線會在一端落在帶內、另一端已跑到帶外,量到的「第一個暗 run 起點」就變成
   上邊界與掃描線的交點而不是符號左緣 —— 2026-08-04 實測繞 Y 軸 25° 時左邊殘差
   **RMS 4.5 px**(門檻 1.5 px),整條路走不通。內插版恆落在帶內。
   掃描線兩端各外延 `crossOverscanRatio × L`:ZXing 的兩個定位點落在最外側暗元素的**中心**
   附近而不是符號左右緣,透視傾斜下上下兩端的左右緣還會再外移,不外延就會把左右緣切在
   掃描邊界上。各條線 `scanlineRuns`:第一個暗 run 的起點得左邊界點、最後一個暗 run 的
   終點得右邊界點(同樣做子像素內插);整條都亮(落在 bearer bar 與條之間的空白)或暗 run
   貼到掃描邊界(被切掉)→ 該條作廢。兩群**各自** `fitLineTLS`。
6. **求交點。** `corners = [上×左, 上×右, 下×右, 下×左]`(順序無所謂,`orderCornersRaw`
   會重排)。兩單位法向的行列式即相鄰兩線夾角的正弦;夾角 < `minCornerAngleDeg` 或交點
   非有限 ⇒ 退回,reason 指名「四線近乎平行,交點在無窮遠」。
   **只檢查相鄰線對**(上×左、上×右、下×右、下×左)—— 上下兩線近乎平行是拍正時的正常
   結果,不得因此判失敗(C1 註)。
7. **信心判準(任一不過即退回,reason 逐項指名實測值 + 門檻,比照 `confidenceReason`):**

   | 項目 | 門檻常數 | 判什麼 |
   |---|---|---|
   | 有效取樣點數 | `minInliers` | 四條線各自的內點數 |
   | 內點比例 | `minInlierRatio` | 四條線各自 `inliers / samples`(分母是實際餵進 `fitLineTLS` 的點數,作廢的取樣位置不算) |
   | 擬合殘差 | `maxRmsPx` | 四條線各自內點的 RMS(px) |
   | 條高 | `minBarHeightPx` | 上下兩線在定位線中點沿 `n` 的距離 |
   | 相鄰線夾角 | `minCornerAngleDeg` | 見 6. |
   | 定位線長度 | `minLocatorLenPx` | 見 1. |
   | 帶內對比 | `minBandContrast` | 見 2. |

通過後把 `corners` 交還 `rectifyQuad`,由既有鏈(`orderCornersRaw` → `quadConfidence` →
`targetRectSize` → `solveHomography` → `warpPerspective`)**再把一次關,不繞過、不放寬**。

**`LINE_FIT_LIMITS`(權威表,已 `Object.freeze` 並匯出;`tests/imgproc.test.ts` 的
`it("1D 擬合門檻為規格 §3.3 的權威值,改動會在此暴露")` 整表 `toEqual`,改程式不改本表
會當場變紅)。** 標「草稿 → 實測」的**兩項**是 2026-08-04 依實測調整、標「新增」的**四項**
是實作補上的(草稿沒預見),理由一律列在同一行 —— 草稿 §3.4 的授權是「可調整但要寫理由
並更新規格」,**兩件事缺一不可**。

| 常數 | 值 | 判什麼 / 為什麼是這個值 |
|---|---|---|
| `samples` | **48**(草稿 24 → 實測 48) | 沿定位線的取樣位置數。1D 符號的暗/亮元素各占約一半,落在空白的位置一律作廢(不補值),有效位置只剩約一半;再扣掉離群,48 才穩定給得出 ≥ `minInliers` 的內點。**草稿的 24 實測只剩約 13 個有效位置,離 8 太近** |
| `crossSamples` | **21**(草稿 9 → 實測 21) | 求左右邊時的掃描線數。ITF-14 的條與 bearer bar 之間有空白間隙,落在間隙的掃描線整條都是亮的、一律作廢,21 條實測會廢掉約 2 條;**草稿的 9 條在同一情境只剩 7 條 < `minInliers`,永遠過不了** |
| `minInliers` | 8 | 每條線的最少內點數。兩點就定得出線,但兩點的線沒有殘差可算、信心無從判斷;8 點在 `maxRmsPx` 下才有統計意義,並與 `QUAD_CONFIDENCE_LIMITS.minEdgePx = 8` 同源 |
| `minInlierRatio` | 0.6 | 每條線的最低內點比例。專擋「點都取到了但散成一片」;作廢過多由 `minInliers` 擋,兩關語意不重疊 |
| `maxRmsPx` | 1.5 | 每條線內點殘差 RMS 上限(px)。子像素內插後合成無雜訊情形殘差 ≪ 1 px;1.5 px 是給實拍的模糊與印刷毛邊留的餘裕,再大就不是一條直線了 |
| `madK` | 2.5 | 離群剔除的 MAD 倍數(`1.4826 × median|r|` 為尺度,即常態下的 σ) |
| `minBarHeightPx` | 12 | 上下兩線在定位線中點的間距(px)。GS1-128 最低條高 13 mm,取樣密度 ≥8 px/module 時遠高於 12 px;低於 12 px 的條高帶擠不下 `crossSamples` 條掃描線 |
| `minCornerAngleDeg` | 20 | 相鄰兩線的最小夾角(度),與 `QUAD_CONFIDENCE_LIMITS.minAngleDeg` 同值同源 —— DLT 在近共線組態下對 1 px 誤差極度敏感 |
| `minLocatorLenPx` | 24 | 定位線最短長度(px)。短於此的兩點連方向都不可信 |
| `searchHalfSpanRatio` | **0.6**(新增,取代草稿的絕對值 `searchHalfSpanPx`) | 沿 `±n` 找條端的搜尋半徑,以**定位線長度的倍率**表示。條高與符號寬是綁在一起的(ITF-14 約 4.5:1、GS1-128 最細長約 12.7:1),**絕對像素值會隨拍攝距離失效**;上下各搜一次,故可涵蓋的條高上限為 **2 × 0.6 = 1.2 倍定位線長**,見下方「條高上限」段 |
| `trackHalfSpanRatio` | **0.08**(新增) | 沿 `±n` 走時每一步重新對準所在暗 run 中心的側向搜尋半徑(見演算法 3.)。0.08 倍符號寬容得下任何單一元素(最寬元素約符號寬的 1/17),又遠小於整條 bearer bar 的寬度 —— 對得準單根條、對不準整條 bearer bar,兩者都是要的行為 |
| `crossOverscanRatio` | **0.15**(新增) | 求左右邊時掃描線往定位線兩端各外延的倍率(見演算法 5.) |
| `minBandContrast` | **24**(新增) | 定位線周邊帶內「亮類平均 − 暗類平均」的最小值(0–255)。Otsu 在單峰直方圖上照樣回得出閾值卻毫無意義,全白/全黑由「某一類是空的」擋下,極低對比靠本項。24/255 ≈ 0.094,與 `roiPhotometric` 的 `edgeContrasts` 同一個尺度 |

**條高上限:基準量是定位線長,不是符號寬(2026-08-04 修正,原文寫錯)。**

原文在 `searchHalfSpanRatio` 那格寫「0.6 對應條高可達**符號寬**的 1.2 倍,連近正方形標籤都涵蓋得到」。
**這句的基準量錯了。** 搜尋半徑是 `0.6 × 定位線長`,上下各搜一次,故條高上限是
**1.2 × 定位線長**。而 ZXing 的兩個定位點落在**最外側暗元素的中心**,定位線長恆**短於**符號寬,
兩者不可互換 —— 換算成符號寬還要再乘 `定位線長 / 符號寬`,該比值隨最外側元素寬度浮動,
**不能只把 1.2 改成別的數字了事**。

2026-08-04 實測(`tests/imgproc.test.ts` 的合成標籤,每模組 12.5 px、無透視無雜訊,二分 24 次):

| 量 | 值 |
|---|---|
| 符號寬(最外側暗元素外緣間距) | 412.5 px |
| 定位線長(最外側暗元素**中心**間距) | 393.75 px(0.9545 × 符號寬) |
| 理論上限 `2 × 0.6 × 定位線長` | 472.5 px |
| **實測邊界條高** | **471.5 px**(= 1.1430 × 符號寬,與理論值差 < 1 px) |

故正確的宣稱是:**條高 ≤ 1.2 × 定位線長**;以本合成圖的比例換算約 **1.14 × 符號寬**。
正方形標籤(條高 = 符號寬)仍在涵蓋範圍內,超出上限則誠實退回「上下邊取樣點不足」。
**未調整 `searchHalfSpanRatio`** —— 調高會同時增加搜尋成本與誤追蹤到鄰近元素的風險,
而現行失效模式是誠實退回(退回代理值)而非假綠,依 §6.1「門檻未經實拍標定不得動」的
同一道理,留待實拍後再定。驗收見 §5.4e。

**取像範圍:條端擬合不可與量測 ROI 共用(2026-08-04 實測發現的整合缺口)。**

階段 ⑤ 收工時 411 個測試全綠,但功能在 `demo/mobile.html` 的實際呼叫端**一次都走不到**。
原因:`inspectReal` 的量測 ROI 是「ZXing 定位點 bbox 外擴 25%(下限 24 px)」,
而 **1D 的兩個定位點 y 幾乎相同 ⇒ bbox 高度 ≈ 0 ⇒ 垂直只外擴到保底的 24 px**,
ROI 高度僅約 48 px,**條的上下端整個落在 ROI 之外**。單元測試餵的是整張合成影像,
故全綠也照樣看不出來。實測(合成 ITF、900×600 相機影像,同一組定位點):

| 餵給 `rectifyQuad` 的影像 | 結果 |
|---|---|
| 量測 ROI(高 **49 px**) | **失敗** —— 上下邊有效邊界點 **0 個 < 8** |
| 整張相機影像(高 600 px) | `ok`,`source: "1d-edges"` |

**修法:另加純函式 `edgeFitRoi(points, imgW, imgH)`,1D 專用的取像範圍。**
垂直半徑取 `searchHalfSpanRatio × 定位線長` —— 與 `quadFrom1DEdges` 的搜尋半徑**同源**,
保證搜尋搆得到的範圍都在裁切內;水平取 `crossOverscanRatio × 定位線長`;
兩軸再各加 `EDGE_FIT_ROI_PAD`(比例 0.15 + 8 px)的餘裕,避免條端正好壓在裁切邊界上被
「不得用畫面邊界當條端」那道守衛擋掉。退化輸入(點不足 / 非有限 / 定位線短於
`minLocatorLenPx`)回 `null`,呼叫端沿用原路徑。

**為什麼不是把量測 ROI 一起放大:** 量測 ROI 一放大就多吃進大片靜區白底,
`roiPhotometric` 的 `rLight` / `rDark` / `edgeContrasts` 會**系統性位移**,而
`policies.ts` 的允收門檻是在舊取樣條件下定的 —— §6.1 明令未經實拍對照不得動。
兩者職責不同,分開算才不會互相污染。`rectifyRoi` 因此改回傳 `{ rect, geo }`,
`geo` 是 `rect.H` 所在的座標系;**焦距與主點必須用 `geo` 換算而非 `rg`**,否則
H 與焦距不在同一尺度,傾角會算錯。

驗收見 §5.4f。

**接進 `rectifyQuad`(唯一入口,既有流程一行不改):**

```
quad = quadFromZxingPoints(points, sym, moduleSizePx)
if (!quad) {
    if (ONE_D_SYMBOLOGIES.includes(sym)) {
        e = quadFrom1DEdges(gray, w, h, points, { sym })
        if (!e.ok) → fail(e.reason)                       // 1D 擬合失敗的具體原因
        quad = { corners: e.corners, derived: false, dimension: null, source: "1d-edges" }
    } else {
        → fail("四角不足（定位點少於 3 個,符號別 …）")
    }
}
```

- **`derived` 必為 `false`** —— 四角是實測擬合出來的,不是推算的;`rectifyPlan` 依既有
  第 3 條規則放行 `useRectified` / `useHomography`,**其判斷邏輯不需要改**。
- `rectifyPlan` 的 `note` 為 `quadSource === "1d-edges"` 加一段「,1D 四角由條端擬合」
  (比照 `qr-alignment`),既有分支字串一字不改。
- **符號別不明(`null` / 空字串 / 不在 `ONE_D_SYMBOLOGIES`)時不啟動 1D 偵測** —— 比照
  上方「符號別不明時一律保守」:寧可退回代理值,不可拿一組意義不明的點去擬合。
- 退回語意 = 「不矯正、沿用現行代理值」,`gray` 必須是 `undefined`(照既有 `fail()` 的
  形狀),**不得**硬套錯矩陣、**不得**代填 0°、**不得** throw(含 `null` / NaN / 空陣列 /
  全白圖)。「四角不足(1D 掃描線僅兩端點,四角偵測**屬階段 ⑤**)」那句退回理由本階段
  之後**必須從程式碼中消失**,`tests/imgproc.test.ts` 有字串守門。

**函式清單:**

簽章依 2026-07-31 程式碼實況,與初版規格略有出入者以本表為準。

| 函式 | 輸入 → 輸出 | 說明 |
|---|---|---|
| `orderCorners(points)` | 4 點 → TL/TR/BR/BL 或 `null` | 以重心極角排序,吃掉各符號別回傳順序不一致;退化由 `quadConfidence` 判定 |
| `quadConfidence(corners)` | 環狀順序 4 點 → `{ ok, areaPx, minEdgePx, fillRatio, minAngleDeg }` 或 `null` | 擬合信心三重把關,門檻見下方「退化門檻」段 |
| `targetRectSize(corners)` | 4 點 → `{ w, h }` 或 `null` | 正射目標矩形尺寸,寬高各取對邊最大值,見下方段落 |
| `solveHomography(src, dst)` | 兩組 4 點 → 3×3 或 `null` | DLT 標準式,8×8 高斯消去,`h33=1`;奇異(四點共線)回 `null` |
| `warpPerspective(gray, w, h, H, outW, outH, maxPixels)` | 灰階 + H → `{ data, w, h, scale }` 或 `null` | 反向映射 + **雙線性內插**;輸出面積受 `MAX_WARP_PIXELS = 4e6` 約束,超出即等比縮小並回報 `scale` |
| `tiltFromHomography(H, focalPx, cx, cy)` | H + 焦距 → 度數 或 **`null`** | 由前兩欄推消失點,得平面法線與光軸夾角;**焦距不可得回 `null` 而非 0**,見下方「焦距來源」段 |

**目標矩形尺寸(`targetRectSize`):** 寬取上下兩邊長的**最大值**、高取左右兩邊長的最大值。

**為什麼取最大而非平均 —— 這條原文寫得太寬,2026-07-31 收窄。** 原文寫「不讓矯正過程降
取樣掉解析度」,**這只在仿射變形下才成立**:仿射時同一條邊上各處取樣密度一致,取最大就
保住了最密的那一邊。**透視情形下不成立** —— 近端本來就比遠端密,矯正是把整個梯形重採樣
到同一個矩形,近端仍會被壓到均值附近。合成實測(繞 Y 軸 25°、每模組 12 px):矯正前同一
條掃描線上模組寬 **10.0–14.5 px**,矯正後 **12.0–12.5 px**,近端的 14.5 px 被壓回 12.5 px。
取最大擋住的是「整體被縮小」,擋不住「近端被壓」。

**所以:矯正不能替代把手機拍正。** 這句要照抄進現場教育訓練的說法,不可省略。矯正把傾斜
造成的**幾何偏差**還原(§1.4 的誤判修掉了),但傾斜當下已經損失的近端取樣密度**還不回來**
—— `resolution` 檢查的 `pxPerModule ≥ 8` 仍得靠拍攝距離與角度去掙,不是靠矯正掙。任何
「矯正過就不用管角度」的說法都與實測不符,亦違反本節末的定位護欄。

**為什麼雙線性不能省:** 最近鄰會在模組邊界造成鋸齒,直接污染 `edgeContrasts` 與 `maxWidthDeviation`。

**退化門檻:`quadConfidence`(2026-07-31 落地,已依程式碼回寫)。**

原本 `orderCorners` 的退化判準只有一條,且與四邊形的外接框尺度綁在一起:

```js
const span = Math.max(maxX - minX, maxY - minY);
if (!(span > 0) || Math.abs(area2) / 2 < 1e-6 * span * span) return null;   // 舊版
```

`span = 1000 px` 時門檻僅 **1 px²**,實質等於「**面積 ≥ 1 px² 就放行**」。這擋得住四點共線
與四點重合,但**擋不住紙片狀四邊形** —— 1000×2 px 的細長四邊形面積 2000 px²,遠高於門檻,
`solveHomography` 會給出一個數值上「合法」、幾何上毫無意義的 H,`warpPerspective` 會把
極薄的來源帶拉伸成整張正射圖,下游 `roi1DGeometry` 還照樣算得出看似正常的
`maxWidthDeviation`,而且不會有任何一條退回路徑被觸發。這是與 §1.3 / §1.5 同一類的病灶:
**檢查存在但實質不擋人**。

改為獨立的純函式 `quadConfidence(corners)`,三重把關、任一項不過即 `ok = false`,由
`orderCorners` 呼叫並在不過時回 `null`。門檻為 `QUAD_CONFIDENCE_LIMITS`(已凍結匯出,
測試直接引用常數而非重寫字面值):

| 門檻 | 值 | 判什麼 | 為什麼是這個值 |
|---|---|---|---|
| `minEdgePx` | **8 px** | 最短邊的**絕對**像素長度 | 與 `resolution` 檢查的 `pxPerModule ≥ 8` 同源 —— 一條邊短於 8 px 連一個模組都放不下,矯正出的細節必然是內插憑空生出來的。**用絕對像素而非相對 `span`,才擋得住紙片狀四邊形** |
| `minFillRatio` | **0.2** | 四邊形面積 / 外接框面積 | 正矩形 1.0、45° 旋轉正方形 0.5、60° 傾角梯形仍 > 0.6,而 5° 透視閘門下的正常符號更接近 1.0。0.2 已是「細長斜帶」等級。共線四邊形此值趨近 0,**本項同時涵蓋舊的共線判定** |
| `minAngleDeg` | **20°** | 四個內角的最小值 | 透視再嚴重,矩形投影的內角也不會小於約 30°;小於 20° 代表兩角幾乎重合或三點近共線 —— DLT 在這種組態下對 1 px 的角點誤差極度敏感,解得出來也不可信 |

**輸入前提(易踩):** `quadConfidence` 要求 `corners` **已是環狀順序**(即 `orderCorners`
的輸出)。非環狀順序會構成自交多邊形,面積與內角都失去意義。輸出
`{ ok, areaPx, minEdgePx, fillRatio, minAngleDeg }`,點數不足回 `null`;回傳實測值而非只回
布林,是為了讓呼叫端能在退回時說明「是哪一項不過」。

**這三個數字有守門測試。** `tests/imgproc.test.ts` 的
`it("門檻數字為規格 §3.3 的權威值,改動會在此暴露")` 直接 `toEqual`
`{ minEdgePx: 8, minFillRatio: 0.2, minAngleDeg: 20 }` —— 改程式不改本節,測試會紅。
這是 C8 規則 JSON(`tests/rules-spec-sync.test.ts`)之外第二個規格↔程式同步機制,
其餘章節(C4.2 / C3.1)仍靠人工回寫,追蹤項見 `docs/todolist20260703-1.md`。

**`tiltFromHomography` 的焦距來源(牽動 §2 的 G4,關鍵)。** 單靠 H **推不出絕對傾角**:
H 只給得到消失線,而同一條消失線在不同視野角的相機下對應不同傾角,必須有**焦距(像素)**
才收斂得出唯一角度。故函式簽章是 `tiltFromHomography(H, focalPx, cx, cy)`,焦距由呼叫端
注入 —— 這與 `src/` 只吃注入數值的架構界線一致。

**不可得時回 `null`,不回 `0`(2026-07-31 落地)。** 初版寫的是「焦距不可得 → 回 0(安全值)」,
**這是錯的**:`gate.ts` 的語意是 `perspectiveTiltDeg ≤ 5°` 否則 FAIL,**0 度是最寬鬆的
放行值,不是安全值**。回 0 等於拿不到焦距就一律綠燈,與 §1.3(即時迴圈 `tilt = 0`)、
§1.5(`pxm = 9`)是**同一個病灶**:用一個安全的假數字讓檢查看起來有在跑。而瀏覽器的
`MediaStreamTrack` 一般拿不到像素焦距,若本函式代填 0,接線後會**恆走**這條路徑,比現行
的臂長差代理值更糟。

現行行為:`H` 為 `null` / 奇異 / 含 NaN,或 `focalPx` 不是有限正數 → 一律回 **`null`**,
不 throw。**退回路徑由呼叫端決定**(例如沿用 `quadGeometry` 的臂長差 `tiltDeg`,並在結果
標註該值為代理),本函式不代填任何放行數字。差別純粹在誠實:`null` 逼呼叫端處理不可得,
`0` 直接放行。

**焦距怎麼來 —— 階段 ④ 接線前必須先定,否則 G4 不成立。** 三個候選,**皆未驗證**:

| 候選 | 做法 | 已知疑慮 |
|---|---|---|
| `getSettings().focalLength` | 直接讀 `MediaStreamTrack` 設定 | 規格有此欄,但機型覆蓋率不明;單位是否為像素需確認 |
| 已知尺寸基準物反推 | 以 §1.7 的參考卡 / 主規劃書 D4 的 26.0 mm 硬幣算 `pxPerMm` 再推 | 依賴「參考卡真實偵測」(尚未實作),與 GSD 同一個前置 |
| 機型對照表 | 查表 | 維護成本高、新機型必然漏 |

三者皆不可得時,依上述退回臂長差代理值 —— **可以退回,不可以填 0 放行**。

**裁示結果(2026-08-03,Eric):採第一候選 + 誠實退回。** 接線時先讀
`track.getSettings().focalLength`,拿不到就退回 `quadGeometry` 的臂長差代理值,
並在結果頁標註該值為代理。落地於三支純函式(皆有 vitest):

- `focalPxFromSettings(settings, imageWidthPx)` —— **單位不明的把關在這裡**。W3C Image
  Capture 的 `focalLength` 各家實作單位不一致(部分回**毫米**,如 4.5),而本專案要的是
  像素焦距。4.5 是有限正數,`tiltFromHomography` 不會拒絕它,會算出一個「看起來像角度」
  的假數字 —— 又是同一個病灶。故本函式:① `settings.width` 可得時把焦距等比換算到分析
  影像尺度(第一層 ImageCapture 的照片寬遠大於串流寬,不換算會低估約 3 倍);
  ② 換算後必須落在 `FOCAL_PX_LIMITS = { minRatio: 0.3, maxRatio: 5 }`(相對分析影像寬)
  的合理帶內,否則回 `null`。數字來源:手機主鏡頭水平視角約 60–80°,
  f = W / (2·tan(FOV/2)) 約 0.6–0.87 W,望遠可到 2–3 W;毫米值在任何影像寬下都遠低於
  0.3 W → 必然被擋。**寧可退回代理值,不可用一個尺度錯的焦距。**
- `resolveTiltDeg(H, focalPx, cx, cy, proxyDeg)` → `{ deg, source }`,
  `source` 為 `"homography"` / `"proxy"` / `"none"`。**兩者皆不可得時 `deg` 為 `null`,
  絕不代填 0**;代理值恰為 0(等臂)則是合法量測值,兩者不可混為一談。
- `TILT_SOURCE_LABEL` —— 結果頁與掃描紀錄的三個文案(「單應矩陣實算」/「臂長差代理值」/
  「未量測」)一律取自此表,不在 HTML 裡另造詞。

追蹤項見 `docs/todolist20260703-1.md`。

**沒選什麼:** 不引入 OpenCV.js。單應矩陣加雙線性重採樣自寫約 120 行,遠比拉進一個 8 MB wasm 划算,且違反「不主動加相依套件」。

**護欄:** 矯正是把拍攝造成的偏差拿掉,讓數值更接近印刷本身狀態。所有等級仍是相對代理值,不因多一道幾何處理就暗示合規性或準確度提升。文案不得出現「校正後即符合」這類說法。

### 3.4b 能力 → 功能 → 降級矩陣(2026-08-05 稽核裁示 D2)

**裁示內容:不限制平台**(iPhone / Android / Safari / Chrome 皆可用),但必須把「平台會怎麼
影響結果」寫下來並在報告上標註。程式面本來就沒有限制 —— 以 `userAgent` / `navigator.platform` /
`userAgentData` / `maxTouchPoints` 掃 `demo`、`src`、`tests` **零命中**,平台字樣只出現在註解與文案。
問題不是「有沒有擋人」,而是**平台沒被擋、但判定結果會被平台決定,而這件事過去沒有寫下來**。

**本矩陣不新增任何門檻,也不改任何既有門檻**(§6.1 凍結仍然有效)。它只規定「缺了某個能力時
降級到什麼、以及必須誠實回報什麼」。

| 能力 | 缺了會怎樣 | 降級行為 | 必須回報 |
|---|---|---|---|
| `navigator.mediaDevices.getUserMedia` | 完全無相機 | 進**示範模式**:等級照出但全程標記為模擬值 | 快門標「示範模式」、結果頁 / 清單 / PDF / XLS 每筆標記,且**不計入通過率分母** |

| `track.getCapabilities()` | 選不出目標解析度 | L2 不可用 → 落 L3 | `requested` 印「未請求」(不得回報從未送出的請求) |
| `getSettings().focalLength` | 無法算像素焦距 | 傾角退回臂長差代理值;1D 連代理值都沒有 → 標「未量測」 | `tiltSource` 三選一:單應矩陣實算 / 臂長差代理值 / 未量測 |

**取樣條件註記的文案規則(硬性):** 只說明取樣密度差異,**不得**寫成準確度、合規或優劣宣稱。
現行實作(`demo/mobile.html` 的 `samplingNote`)在 `shot.path` 非 L1 或 `roiScale < 1` 時附加:

> 本張未走照片解析度取幀(L3/drawImage)。取樣密度會影響 DEC / EC 這類代理值的絕對數字,
> 與不同取樣密度下的紀錄**不宜直接互比**;同一台裝置、同一取幀層別的前後比較才有意義。

**尚未查證(不可當事實引用):** 「Android 判 A/B、iPhone 判 D/F」是**外推不是實測** ——
repo 內沒有任何 iOS 實拍數據,L2 實際能升到多少取決於 Safari 的 `getCapabilities()`。
門檻是否需要依取樣密度重新標定,依 §6.1 一律等實拍對照,本輪不動。

### 3.4c 可量測性判定(2026-08-05 稽核裁示 D4)

**裁示內容:量不到就不出等級。** 過去三條路徑都會產出一個看起來正常的等級與「通過/未通過」:

1. **解碼失敗** → ROI 退回「畫面中央 70%」,拿任意像素算出等級(稽核 IMG-09)。
2. **1D 掃描線全滅**(最常見成因是條碼橫躺 90°,量測沿影像水平列掃描)→ 落到硬寫的
   `{0.5, 0.5, 0.5}` 最差值 → 判 **F、未通過**,且不告訴使用者原因(稽核 IMG-04)。
3. **無相機的示範模式** → 情境模擬值走完整條結果頁 / 清單 / PDF,**沒有任何文字標記**(稽核 IMG-03)。

判定由純函式 `assessMeasurability`(`demo/imgproc.js`)負責,**不得寫進 HTML** ——
`demo/*.html` 無自動化測試可覆蓋,寫進去就再也驗不了(這條紀律 2026-08-04 已經咬過一次)。

| 情況 | `measurable` | 行為 |
|---|---|---|
| 正常 | `true` | 照常出等級與判定 |
| 解碼失敗 | `false` | **不出等級、不出通過/未通過**;顯示「不可量測 — 影像中找不到可解碼的符號」 |
| 1D 掃描線為 0 | `false` | 同上,原因為「掃描線全數不可用」;定位線角度 ≥ `ROTATED_HINT_MIN_DEG`(45°)時另給「條碼橫躺,請轉正後重拍」 |
| 示範模式 | `true`(但 `simulated`) | 等級照出(抽掉的話示範模式失去意義),**但全程標記且不計入通過率** |

**為什麼示範模式不比照「不出等級」:** 稽核 IMG-03 指的是「沒有標記」,不是「不該有等級」。
示範模式的用途就是在沒有相機時展示結果頁長什麼樣子。

**護欄:** 「不可量測」的措辭只描述「量不到」這件事實,**不得暗示符號本身品質好壞** ——
量不到不等於印壞了。`tests/imgproc.test.ts` 有一條守門測試掃 `ISO` / `合規` / `不合格` / `印壞` 等字樣。

### 3.4d 光度量測基底與幾何分離(2026-08-05 稽核裁示 D3)

**裁示內容:幾何吃正射影像,光度留在未矯正 ROI(只對 1D)。**

1D 一旦走矯正,光度取樣區域從「定位點 bbox 外擴 25%(含靜區)」整塊換成「符號四角內的正射
重採樣影像」—— 兩者量的根本不是同一塊像素:正射範圍把 bearer bar 含了進來,而
`roi1DGeometry` 的 `slice(1, -1)` 又剔掉最外側真條。

**實測(合成 ITF-14,繞 Y 軸 25°,`tests/imgproc.test.ts`「光度量測基底對照」):**

| 量 | 未矯正 ROI | 矯正影像 |
|---|---|---|
| `minEdgeContrast` | **> 0.3**(健在) | **0.000**(至少一條掃描線量到 0) |
| `rLight` / `rDark` | — | 兩側差距 < 0.25(**證明不是矯正把影像弄糊**,是取樣範圍不同) |

0° 拍攝同樣成立 → **與傾角無關,是取樣範圍的差異**。

而 `src/data/policies.ts` 的允收門檻依 §6.1 是凍結的 —— **門檻與量測條件被拆開了**。
本輪的最小止血是把兩件事分開:`useRectified` 時 1D 的幾何吃 `rect`、光度吃 `rg`,
**門檻一行不動**。2D 維持原樣(GNU/FPD 本來就依賴正射幾何,且無 bearer bar 問題)。

取樣密度規則(低於某密度就關掉 `useRectified`)**本輪不做** —— 它需要一個實拍標定過的門檻值,
等 §5.2 的實機數字回來再加,加的地方確定是 `rectifyPlan`。

### 3.5 1D 元素計量的重新設計(2026-08-05)

**動機:兩個在「像素完美、零雜訊」合成圖上就成立的失效** —— 與鏡頭 / 光線 / 拍攝技巧全都無關,
所以前幾輪「多次改版與實測都數不對」不是調參數能解決的。

| 失效 | 內容 | 實測 |
|---|---|---|
| **A · 量測模型套錯符號別** | `roi1DGeometry` 對所有 1D 符號一律算「元素寬 ÷ 模組寬,離最近整數多遠」。這對**模組型**(Code 128 / QR / DataMatrix)對,但 **ITF-14 是雙寬符號** —— 寬窄比允許 2.0–3.0,GS1 建議 2.5,離最近整數剛好 **0.5** = 容差 | DEC **0.00(F)**,且 6 / 12 / 24 px/元素**全部一樣**。提高解析度永遠無效 |
| **B · 模組寬被量化成整數像素** | `scanlineRuns` 以整數像素切 run,模組寬取十百分位 ⇒ 永遠是整數;實拍時每模組像素數幾乎不可能是整數 | 5.5 px → DEC 0.80(F);9.7 px → 3.20(B);14.2 px → 3.43(A/B)。**同一張完美圖,只是換個距離拍** |

**取樣密度掃描實測**(同一張完美合成圖,6.0→14.0 px/元素,0.1 步進):
現行演算法等級擺動 **2.67 級**(ITF 0.00→2.67、模組型 1.33→4.00),
而 ITF-14 的允收門檻只差 C 一級 —— **同一個箱子,站近一點拍會過,站遠一點就不會過**。

#### 流程(對應 `demo/imgproc.js` 的 `roi1DMetrology`)

| 步驟 | 做法 | 對應 ISO/IEC 15416 |
|---|---|---|
| S2 | **合成孔徑**:弦權重核 `w(x)=2√((d/2)²−x²)`,直徑 **0.5 × 模組寬**(`GEOMETRY_APERTURE_X`) | 量測孔徑。空間低通,抹平比孔徑細的紙紋 / 楞痕 / 網點 |
| S3 | 全域門檻 `GT=(Rmax+Rmin)/2`,逐掃描線各自求 | 掃描反射剖面 |
| S4 | **次像素邊界**:剖面穿越 GT 的線性內插位置 | 元素邊界判定 |
| S5 | **元素數驗證**:對不上標稱值 → 該掃描線作廢 | — |
| S6 | **由解碼結果取回標稱序列**(`itfNominalPattern`) | 參考解碼演算法 |
| S7 | 模組寬擬合:雙寬取窄/寬**中位數**;模組型以 `總跨距 ÷ 總模組數` 為錨 | — |
| S8 | 可解碼性依符號別分流:雙寬量**窄/寬判別餘裕**;模組型用 **E2SE** | 各符號別自己的參考解碼演算法 |

**孔徑為何不必等實拍對照(修正 2026-08-05 早先的判斷):** 原本認為孔徑「會系統性改變 SC / MOD / 缺陷」
故須排在實機驗收後。裁示 D3 把光度與幾何拆開之後那個理由不再成立 ——
**孔徑只施加在幾何掃描線上,`roiPhotometric` 完全不經過它**,故不觸及 §6.1 的門檻凍結。
而它正是抗雜訊的主要機制,少了它次像素邊界會在實拍雜訊下炸出假邊界。

#### 模組型為何用「總跨距 ÷ 總模組數」而非無約束擬合

無約束的模組寬估計在**墨量增益**下會收斂到錯誤的局部解 —— 實測:條各胖 0.3 模組、空各瘦 0.3 模組時,
迭代擬合收斂到 module **8.56**(真值 12)、標稱序列整組錯位,DEC 與 BWR 一起被污染。
**柔印墨量增益正是瓦楞箱的主要劣化,不能在那個情境下失效。**

Code 128 的結構是固定的(ISO/IEC 15417):start / 每個資料字元 / check 各 **6 元素 11 模組**,
stop **7 元素 13 模組** ⇒ `元素數 E = 6n+19`、`總模組數 = 11n+35`(`code128TotalModules`)。
於是 `w = 總跨距 ÷ 總模組數` 是閉式解、沒有歧義,且**對稱的墨量增益不改變總跨距**,天生免疫。
捨入後的總模組數必須對得回去,否則就是數錯了 → 該掃描線作廢。

#### E2SE 的效果(實測,非宣稱)

條各胖 0.3 模組時,同一組量測下:

| 量 | 最差殘差 | 對應 DEC |
|---|---|---|
| 元素逐一殘差 | **0.330** 模組 | 1.36(D) |
| **E2SE 殘差** | **0.054** 模組 | 3.57(A) |

污染降到約 **1/6**。**不是歸零** —— 條 22 個、空 21 個並不相等,總跨距淨移 +0.3 模組,
讓模組寬偏約 0.9%,這一點 E2SE 擋不掉,誠實記錄。
`elementResidualWorst` 保留在輸出中僅供診斷與守門對照,**不參與評級**。

#### 已知限制(未做)

- **Code 128 的完整參考解碼表(103 個樣式)未實作。** 模組型走的是「結構錨定 + 捨入」,
  拿掉了整數量化(失效 B)也擋掉了墨量增益,但標稱序列是**推得的不是解碼得來的** ——
  若元素數恰好符合結構卻其實數錯,不會被抓出來。ITF-14 走的是真正的參考重建(S6),無此問題。
- **逐掃描線評級後平均(ISO 的聚合順序)未做。** 那要動 `src/engines/grade.ts`,影響面最大,
  依落地順序排在實拍數字回來之後。
- **一次實拍都沒有。** 全部是合成圖與假相機。合成綠燈 ≠ 實拍可用。

#### 守門規則(新增)

**任何量測改動都必須附一組「取樣密度掃描」測試**:同一張合成圖在 6.0–14.0 px/元素之間
以 0.1 步進各跑一次,斷言等級**擺動 < 0.25 級**。
這條會直接擋下失效 B 這一整類病 —— 而**改動前的 431 個測試全數漏掉它**,
因為既有測試都在固定的整數取樣密度上跑,剛好落在不會出錯的那些點。

### 3.7 快門延遲下的取幀誠實性(2026-08-06)

> 由來:實機回報「相機拍照與取像似乎會有延遲,導致拍照有問題、無法判斷品質」。
> 追下去是兩個**與影像演算法無關**的時序缺陷。

#### 病灶

```
t = −500…0 ms   measureFrame 量「預覽」幀 → 對焦/眩光/楞痕/白平衡 → 燈號綠、快門 ARMED
t = 0           按下快門 → inspecting = true → 即時量測整段停止
t = 0…800 ms    L1 takePhoto()(手機快門延遲,且會重跑 AF/AE)
t = 0…500 ms    L2 applyConstraints 升壓 → waitForVideoWidth 一到目標寬就放行
t = T           **這一張**才是被解碼、被分級的影像
```

**缺陷 ① 判定的幀不是被分析的幀。** 燈號依據的是快門前 ≤500ms 的預覽,被分級的是快門後
≤800ms 的照片,最壞相隔約 **1.3 秒**;手持位移與相機重新對焦全發生在這個窗口裡,
而系統裡沒有任何一處會發現。更嚴重的是 §3.4 的「本張閘門」(裁示 D5③)——
它的原意是記錄這張照片的實際拍攝品質,但光度四項讀的是 `state.gate` 的預覽殘值,
**從未量過被分析的那張影像**。報告印「本張閘門 全部 OK」時,那四欄講的是另一張影像。

**缺陷 ② L2 抓的是模式切換後的第一幀。** `applyConstraints` 換解析度等於換相機模式,
AE/AF 會重新收斂,而 `waitForVideoWidth` 一到目標寬就放行 —— 放行的正是收斂中的那一幀。

#### 修法

**核心不是把延遲消掉**(消不掉:`takePhoto` 的延遲在瀏覽器與韌體裡),
而是**把判定改成量在被分析的那張影像上** —— 延遲多久都不影響結論的正確性。

| # | 改動 | 位置 |
|---|---|---|
| F1 | 抽出 `measureQuality(src, w, h)`,預覽與快門照走**同一條 320px 取樣路徑**;`shotGate` 改吃照片自己的讀數 | `mobile.html` |
| F2 | 實測並記錄快門延遲毫秒數 + 對焦相對預覽比值,進 `lastShotInfo` → 清單 → PDF | `mobile.html` |
| F3 | `assessShotFreshness` 純函式:「預覽過了、照片沒過」→ 具名告警並建議重拍 | `imgproc.js` |
| F4 | L2 升壓協商完成後多等 `SETTLE_FRAMES`(3 幀 / 上限 200ms)讓 AE/AF 沉澱 | `mobile.html` |
| F5 | 快門忙碌標籤由「檢驗中…」改為「**拍攝中 — 請維持不動**」 | `mobile.html` |

**取樣寬固定 320 是量測前提,不是效能取捨。** `varianceOfLaplacian` 隨取樣密度系統性變動,
而對焦門檻(`policies.ts`,依 §6.1 凍結)校在這個尺度上。兩邊走同一尺度,同一組門檻才適用。

#### 刻意不做的事

- **不拿「照片 varLap ÷ 預覽 varLap」的比值當判準。** 兩者雖同為 320px,來源尺度不同
  (預覽由 1280 縮下來、照片可能由 4032 縮下來),後者抗鋸齒平均更重,比值本身帶系統性偏差。
  本輪探針實測到同景比值在 **1%–137%** 之間擺動,足以證明未校準前不可當門檻。
  比值仍算出來並記錄,**只作診斷數字**。
- **不改分級、不動任何門檻、不鎖快門**(沿裁示 D5 先例:閘門與分級是兩套語意)。
  告警放在等級**上方**,讓使用者先看到「這張不可採信」再看到那個字母。
- **`SLOW_SHUTTER_MS`(400)只決定要不要在延遲數字旁加註「偏慢」**,不參與任何判定。

#### 待校準(需 §5.2 實機資料)

`SETTLE_FRAMES = 3` 與 `SLOW_SHUTTER_MS = 400` 都是**推理值不是量測值**。
F4 本身會增加約 100ms(30fps 下 3 幀)延遲 —— 方向與使用者的抱怨相反,
之所以仍採用,是因為它換到的是「被分析的幀是可用的」;而**就算等不夠,F1 也會把
糊掉的那張抓出來告警,不會靜默出等級**。實機資料回來後兩個常數都要重新定。

### 3.4 提案 C — 相機補光(torch)

Web 端沒有閃光燈,只有**常亮手電筒**,是 `MediaStreamTrack` 的約束,須在串流開啟後對 track 下。

```js
const track = stream.getVideoTracks()[0];
const caps  = track.getCapabilities?.() || {};
const hasTorch = "torch" in caps;
await track.applyConstraints({ advanced: [{ torch: on }] });
```

| 平台 | 支援 | 做法 |
|---|---|---|
| Android Chrome | 是 | 顯示切換鈕,狀態同步自 `track.getSettings().torch` |
| iOS Safari | 否 | `caps.torch` 不存在 → 不顯示按鈕,不放無效控制項 |
| 桌面瀏覽器 | 通常否 | 同上,靜默隱藏 |

**三條規則:**

1. **永遠手動,絕不自動開燈。** 現場刺眼、耗電,且自動補光會在使用者不知情下改變同批貨的拍攝條件 —— 這條產品線的價值建立在條件一致上。
2. **torch 不得成為閘門條件。** 不進 `GateMeasurements`、不影響 ARMED/LOCKED 判定。
3. **停止串流前先關燈。** 現行 `stopCamera()` 直接 `track.stop()`,部分機型會留著燈不熄。

**與 glare 的交互:** 近距離補光打在上光面或銅版標籤上,`glareRatio` 會飆到 >4% 而 FAIL 鎖死快門。**不得為此放寬 glare 門檻** —— 門檻是對的,反光的照片本來就量不準。正確做法是在 glare 因開燈而 FAIL 時提示「關閉補光或改變角度」,並把 `torchOn` 記進該筆掃描紀錄以供事後追溯。

|---|---|
| 取幀 | `L2/applyConstraints` · 1280×720 |
| 解碼 | ✓ DataMatrix · `M-CODE-QC-14712345678907-DM` |
| 定位點 | **4 個真角點**(非 QR 那種三角 + alignment),`quadFromZxingPoints` 走「四點即四角」 |
| **結果頁** | **「幾何量測:已矯正 389×390;透視傾角 0.4°(單應矩陣實算)」** |
| 判定 | 通過(門檻 ≥ C,margin 0.02);等級 C,最弱項 MOD C(1.52) |

389×390 對上合成的 400×400 有獨立解釋:ZXing 的角點落在**角落模組的中心**
(105 而非 100、494 而非 499),105→494 = 389。傾角 0.4°(真值 0°)是角點量化的殘差,
落在容差內且誠實標為實算,未被代填成 0。

**至此三條 2D/1D 分支全部實跑過**:1D(§5.4g)、QR v≥2(§5.4c)、DataMatrix(本節)。

## 6. 風險與未決

### 6.1 待驗證假設(尚未查證,不可當事實)

- **`varLap` 門檻的解析度相依性。** `varianceOfLaplacian` 的絕對值與取樣密度有關,現行 ≥120 是在 320 px 即時影像上定的。即時迴圈維持 320 px 故本次不受影響,但**若日後把幾何檢查即時化、改用更大的預覽幀,此門檻必須重新標定,不得沿用**。
- **同一道理適用於 `roi1DGeometry` 的 `maxWidthDeviation`(DEC)與 `roiPhotometric` 的 `edgeContrasts`(餵給 MOD)。** 這兩個代理值原本量在 ≤1024 px 的分析影像上,階段 ① 拿掉 1024 硬砍後取樣密度大幅提高,量出來的數字會**系統性位移**。位移的機制是量化誤差:模組寬從約 3.5 px 變約 14 px,±0.5 px 的量化誤差佔比從 **0.14 模組降到 0.036 模組**,`maxWidthDeviation` 會系統性變好;`edgeContrasts` 取的是相鄰 run 平均亮度差的最小值,run 變長後純內部像素比例上升、受邊緣模糊污染變少,也會跟著位移。**而 `src/data/policies.ts` 現行的允收門檻(ITF-14 ≥C、GS1-128 ≥B)是在舊取樣密度下調出來的。**

  **本輪已新增特性化測試記錄此影響**(`tests/imgproc.test.ts` → `describe("特性化:取樣密度對 DEC 代理值的系統性影響(記錄用,非允收門檻)")`,固定合成圖樣、無亂數)。2026-07-31 實測:

  | 取樣密度 | 對應情境 | `modulePx` 估值 | `maxWidthDeviation` | 推算的 DEC 字母 |
  |---|---|---|---|---|
  | 每模組 3.5 px | 1024 px 寬 / 視野 300 mm | 3 | **0.3333** | D |
  | 每模組 14 px | 4032 px 寬 / 視野 300 mm | 14 | **0.0000** | A |

  同一個「完美」的合成條碼,**只換取樣密度就從 DEC=D 變 DEC=A**(字母由實測值依 `grade.ts` 的 `DEC = 1 − maxWidthDeviation / tolerance`、`tolerance = 0.5`、`ratioToScore` 與 `scale.ts` 的帶下界推算,非測試直接斷言)。根因是「最窄 run 的 10 百分位」模組寬估計在低取樣密度下被量化低估:7 px 的雙模組元素除以估成 3 px 的模組寬得 2.33,偏差 0.33 全被記成印刷缺陷。

  **`edgeContrasts` 的位移方向與量級尚未量測 → 未驗證**,上述機制為程式碼推理,本輪沒有做對應的特性化測試。

  **門檻是否需重新標定,待 8765 測試台以同一標的做「提高解析度前 / 後」實拍對照後決定。** 在對照做出來之前,不得調整 `policies.ts` 的任何允收門檻,也不得把上表數值當成品質標準。
- **視野 300 mm 的假設。** §1.5 的算式基於「條碼與比例尺卡並排入鏡」的實務估計,尚未以實機量測驗證。實際視野若更小,結論只會更嚴格,不會更寬鬆。
- **`getPhotoCapabilities()` 的機型覆蓋率。** 已知 Android Chrome 支援,但各廠牌回報值是否可信未實測。

### 6.2 已知風險

- 階段 ⑤(1D 四角偵測)風險最高,GS1-128 無 bearer bar 可依靠。若實拍失敗率過高,可只保留 2D 矯正並在報告載明 1D 走退回路徑。
  **2026-08-04 更新:合成情境下 GS1-128 與 ITF-14 同樣在 ±1° 內(見 §5.4d),沒有用到本條退路;
  但合成圖沒有印刷毛邊、紙面起伏與雜訊,`maxRmsPx = 1.5px` 這一關在實拍下的誤拒率仍是未知數
  —— 本條風險改為「實拍未驗」而非「已解除」。**
- 提高解析度後 `pxPerModule` 上升,原本被假值掩蓋的 `resolution` WARN/FAIL 會開始真的出現。**這是修好了,不是壞了** —— 但需在文案與教育訓練上先說明,避免現場誤以為系統變嚴格了。
- **低取樣密度下,對 1D 做矯正會讓 DEC 代理值變差(2026-08-04 實測,尚未決定怎麼處理)。**
  階段 ⑤ 之前 1D 從來拿不到四角、永遠不矯正,量測吃的是原 ROI;修好 `edgeFitRoi` 之後
  1D 開始真的走矯正,量測改吃正射影像 —— 這是**行為變化**,而正射重採樣要付一次雙線性
  內插的模糊代價。同一張合成 ITF(0° 拍正、無透視可矯正)實測:

  | 每模組 px | 未矯正 `avgMaxDev` | 已矯正 `avgMaxDev` |
  |---|---|---|
  | **5** | 0 | **0.5(飽和,DEC 直接掉到 F)** |
  | 8 | 0 | 0 |
  | 12 | 0 | 0 |

  **退化只在低取樣密度發生,8 px/module 以上就消失**,機制與 §6.1 記載的同一個:
  模組寬估計器取「最窄 run 的 10 百分位」,5 px 下重採樣把 run 長度推成 4/5/6 混雜,
  估值落到 4,`run / module` 全部變成 x.5 ⇒ 偏差飽和在 0.5。
  §1.5 估計實拍(4032 px 寬)約 14 px/module,落在安全區,故**本輪不改行為** ——
  要不要依取樣密度把 `useRectified` 關掉,屬 §6.1「未經實拍對照不得動門檻」的同一類決定,
  需要「提高解析度前 / 後」的實拍數據才談得上。**8765 實機驗收時要順帶記下 1D 的
  `pxPerModule` 與 DEC 字母**,那組數字才是判準。
- **1D 四角偵測的條高上限。** 條高超過 `1.2 × 定位線長`(本檔合成圖約 1.14 × 符號寬)時
  `quadFrom1DEdges` 誠實退回「上下邊取樣點不足」,1D 就回到沒有真傾角的舊狀態。
  ITF-14(約 4.5:1)與 GS1-128(最細長約 12.7:1)的正常條高遠在上限之內,**但條高極大的
  非標準標籤會落在退回路徑**。失效模式是退回代理值而非假綠,故不急著調
  `searchHalfSpanRatio`;要調須先有實拍對照(理由與量測見 §3.3「條高上限」段,驗收見 §5.4e)。
