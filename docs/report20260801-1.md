## 2. 做了什麼

### 2.1 `CaptureQualityReport` 的 `gsdMmPerPx` / `pxPerModule`:`number` → `number | null`

改動前不可得是以 **`NaN`** 承載。NaN 的問題不是風格,是三條實際傳染路徑:

| 路徑 | NaN 的行為 | null 的行為 |
|---|---|---|
| `JSON.stringify`(報告隨 `InspectionSession` 送 ERP,C9) | 靜默變成 `null` —— 報告裡是 NaN、ERP 收到 null,兩種表示法並存 | 往返前後一致 |
| `toFixed()` / 字串插值 | 印出字面 `"NaN"` | 呼叫端被型別逼著先處理 |
| 任何算術 | 一路污染下去,而型別上仍是合法 `number`,`strict` 也不會攔 | 型別即防線 |

`pxPerModule` 一併放寬 —— 它用的是同一套 NaN 承載法,只改一半等於留一半的坑。

**消費端全部掃過,結論是無呼叫端需要改**(故無行為變更,只是把不可得從型別上暴露出來):

- `src/export/csv.ts` — §C9.4 欄位清單本來就不含這兩欄。
- `src/erp/client.ts` — 不觸及 `capture`。
- `demo/index.html` / `demo/mobile.html` — 只往 `evaluateGate` **傳入**,不讀報告的這兩欄。

`GateCheck.value` **維持 `-1` 哨兵值不變**,這是刻意的:該欄型別是 `number`,放不進 `null`;
報告頂層放得進就不該退而求其次。兩處表示法不同的判準寫進了規格 C4.2,也寫進了守門測試。

### 2.2 `tests/gate-spec-sync.test.ts`(新檔,36 個測試)

比照 §C8 既有的 `rules-spec-sync.test.ts`,直接解析主規劃書再與程式比對。涵蓋:

| 規格處 | 守什麼 |
|---|---|
| C4.2 六項檢查表 | key 與順序 = `classifyChecks` 前六項;每項 OK/WARN/FAIL 三欄的**門檻數字** |
| C4.2 附加段 | 透視 ≤5° 的門檻數字 |
| C4.2 解析度兩支表 | 兩支的判定與**兩個 `threshold` 字串逐字**;GSD 不可得分支的 `pxPerModule` 門檻必須與可得分支同數字(少一個條件 ≠ 降低標準);文案不歸因 |
| C4.2 「不可得」守衛表 | 逐列:各檢查在 `null` / `undefined` / `NaN` 下的狀態 |
| C4.2 哨兵值段 | `GateCheck.value` 不可得時 = 規格寫的 `-1`,且所有 value 恆為有限數 |
| C3.1 型別宣告 | `CaptureQualityReport` 的欄位名、順序、型別**逐字**比對 `src/domain/types.ts` |

三個設計決定,寫在檔頭註解裡:

1. **比對行為,不比對程式碼字面。** 門檻寫在 `if` 判斷式裡,比字面等於是把規格再抄一次;
   本檔是把規格的 `≤1%` / `1–4%` / `>4%` **還原成邊界值再實跑 `classifyChecks`**。
2. **解析不出來就讓測試紅**,不靜默略過。「看不懂的欄位就不測」正是漂移躲過守門的方式,
   故無法解析的儲存格會走到一個 `expect.fail` 的分支。
3. **守衛表的委派列要名副其實。** `resolution`:`gsd` 那列寫「走上表 GSD 不可得分支」,
   本檔不接受這句話本身,而是實跑確認 `null` / `NaN` / `undefined` 三者拿到的
   `threshold` 與上表逐字相同。

## 3. 抓到的東西

### 3.1 一筆真實的規格漂移(施工當下就紅)

C4.2 六項檢查表的 `whiteBalance` 列停在:

```
| whiteBalance | 參考卡白塊 RGB 增益偏差 | Δgain | ≤5% | — | >5%（要 AWB lock） |
```

也就是 **>5% → FAIL(鎖快門)**。但程式是 `wbGainDeviation <= 0.05 ? "OK" : "WARN"`,
且**同一節下方**的「不可得」守衛表白紙黑字寫「建議燈永不 FAIL 是本節既有性質」,
專案 `CLAUDE.md` 也把白平衡列為**歷史誤判熱區**(建議燈,不鎖快門,不要改回硬閘門)。

同一節的表格與散文互相矛盾,而表格是先被讀到的那個。**修規格、不動程式**:FAIL 欄改為
`—`、WARN 欄改為 `>5%(建議 AWB lock)`,並在表下加一段說明「FAIL 欄的 `—` 是不存在,
不是漏填」,附理由與這次的沿革。

守門那側同時把它變成機制:規格標 `—` 的欄位,測試會**掃過 0 到 20 倍門檻的讀數**斷言該
狀態永不出現,並額外斷言 100 倍門檻下閘門仍不 `LOCKED`。日後有人想把建議燈改回硬閘門,
必須先改規格,改了規格又會撞上其他測試。
